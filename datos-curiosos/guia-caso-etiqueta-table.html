Introducción — una etiqueta usada para algo distinto a lo que fue creada
El caso de <table> es, quizás, el ejemplo más famoso

Pocas etiquetas de HTML tienen una historia tan curiosa como <table>. Se diseñó para una sola cosa: mostrar datos tabulares, como una hoja de cálculo. Pero durante casi una década, se convirtió en la herramienta principal para construir el diseño completo de una página web — columnas, barras laterales, encabezados — porque, sencillamente, no existía nada mejor que funcionara de forma confiable en todos los navegadores.

💡 El dato en una frase

Entre mediados de los 90 y mediados de los 2000, los diseñadores web usaron tablas HTML —pensadas para mostrar datos— como herramienta principal de maquetación, porque el CSS aún no tenía soporte confiable para layouts. El movimiento de estándares web de principios de los 2000 fue el que finalmente empujó a la industria a abandonar esa práctica.

🗂️
<table>: pensada para datos, usada para maquetar
Cuando la única herramienta confiable era la equivocada

La etiqueta <table> se estandarizó formalmente en HTML 3.2 (1997), con la intención explícita de representar datos organizados en filas y columnas. Pero los diseñadores de la época descubrieron que las tablas también resolvían, de forma indirecta, un problema que el CSS todavía no sabía resolver bien: dividir la página en columnas y colocar elementos exactamente donde se quería.

🧱 Analogía: usar una caja de herramientas incompleta

Es como si, para colgar un cuadro, solo tuvieras un martillo de carpintero de obra y ninguna herramienta más pequeña. No es la herramienta ideal, pero si es la única que tienes y funciona igual de bien en todas las paredes, la vas a usar. Eso pasó con las tablas: el CSS de layout (posicionamiento, columnas) apenas empezaba a estandarizarse, y su soporte entre navegadores era muy inconsistente, así que las tablas —que sí funcionaban igual en todos lados— se volvieron el martillo de todos los usos.

🪆
El infierno de las tablas anidadas
Cuando un diseño de tres columnas significaba diez tablas dentro de tablas

Para lograr diseños más complejos, los desarrolladores metían tablas dentro de tablas —a veces con varios niveles de anidación— solo para controlar el espaciado y la posición de cada sección de la página. Este enfoque se ganó un apodo poco cariñoso en la comunidad: "tag soup" (sopa de etiquetas) o, más específicamente, "table-based layout hell".

ProblemaPor qué ocurría
Código difícil de leerUna página con tres columnas podía requerir docenas de etiquetas <table>, <tr> y <td> anidadas.
Carga más lentaEl navegador no podía renderizar la tabla hasta tener todo su contenido, lo que retrasaba la visualización de la página completa.
Accesibilidad pobreLos lectores de pantalla interpretaban el contenido como datos tabulares, confundiendo a usuarios con discapacidad visual.
Imposible de reutilizarCambiar el diseño de la página implicaba reescribir HTML, no solo estilos.
📢
El movimiento de los estándares web
Cuando la comunidad empezó a decir "esto se puede hacer mejor"

A principios de los 2000, figuras como Jeffrey Zeldman, cofundador del Web Standards Project (WaSP), y publicaciones como A List Apart, empezaron a promover activamente el "CSS-based layout": usar CSS para maquetar, y reservar el HTML únicamente para el contenido y su estructura semántica.

🟢 Argumentos que usaba el movimiento

  • Separar contenido y diseño hacía el código más fácil de mantener y actualizar.
  • Las páginas cargaban más rápido, al reducir la cantidad de etiquetas necesarias.
  • Mejoraba la accesibilidad para lectores de pantalla y otras tecnologías de asistencia.
  • Un mismo HTML podía verse distinto simplemente cambiando la hoja de estilos, sin tocar el contenido — la idea que después popularizó CSS Zen Garden en 2003.

El propio <table> se convirtió, en cierto modo, en el símbolo de todo lo que el movimiento de estándares quería dejar atrás: una etiqueta usada para un propósito que nunca fue el suyo.

🏆
El "Holy Grail Layout"
El diseño de tres columnas que se volvió el examen final del CSS puro

Lograr un diseño clásico de tres columnas —encabezado, barra lateral izquierda, contenido central, barra lateral derecha, pie de página— usando solo CSS (sin tablas) se volvió tan complicado con las herramientas disponibles en ese momento (principalmente float y posicionamiento) que la comunidad lo apodó en broma el "Holy Grail Layout" (el santo grial del layout), en referencia a lo esquivo que resultaba conseguirlo bien en todos los navegadores.

⚠️ Por qué tardó tanto en resolverse bien

Durante años, lograr columnas de igual altura, en el orden correcto y sin que se rompieran en navegadores más antiguos, requería técnicas ingeniosas pero frágiles con float y márgenes negativos. El problema no se resolvió de forma realmente cómoda hasta la llegada de Flexbox (adopción amplia hacia 2013-2015) y, después, CSS Grid (2017), que finalmente le dieron al CSS herramientas de layout diseñadas específicamente para eso.

Lo que queda hoy: <table> de vuelta a su trabajo original
Con Flexbox y Grid, la etiqueta pudo por fin jubilarse del layout
🗂️
Table-based layout
La práctica, hoy considerada obsoleta, de usar tablas HTML para construir la estructura visual de una página en vez de mostrar datos.
🌊
float
Propiedad de CSS usada originalmente para que el texto rodeara imágenes, adaptada durante años como técnica improvisada de layout.
📐
Flexbox
Sistema de layout de CSS pensado para distribuir elementos en una sola dirección (fila o columna) de forma flexible.
🔲
CSS Grid
Sistema de layout de CSS pensado para estructuras de dos dimensiones (filas y columnas a la vez), publicado como recomendación en 2017.

💡 Resumen del dato curioso

La etiqueta <table> se creó para mostrar datos, pero durante casi una década fue la herramienta de facto para maquetar páginas web enteras, porque el CSS de layout aún no era confiable entre navegadores. El movimiento de estándares web de principios de los 2000 empujó el cambio hacia CSS puro, un camino que solo se completó realmente con la llegada de Flexbox y CSS Grid — herramientas diseñadas, esta vez sí, específicamente para resolver el problema que las tablas resolvían por accidente.
