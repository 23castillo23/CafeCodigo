Introducción — un ecosistema que nunca deja de moverse
React, Vue, Angular, Svelte, Solid... ¿y por qué tantos?

Si empiezas a investigar cómo construir un sitio web hoy, es fácil sentirte abrumado por la cantidad de nombres: React, Vue, Angular, Svelte, Solid, Ember, Preact... Esta sensación es tan común que hasta tiene nombre propio en la comunidad de desarrollo: "JavaScript fatigue" (fatiga de JavaScript).

💡 El dato en una frase

Existen tantos frameworks de JavaScript porque el ecosistema es de código abierto, tiene una barrera de entrada relativamente baja para crear herramientas nuevas, y cada framework surgió resolviendo un problema específico de su época —desde manipular el DOM más fácil hasta construir aplicaciones enteras dentro del navegador.

🧰
jQuery: el problema que todos tenían
2006 — cuando manipular el DOM era una pesadilla de compatibilidad

Antes de que existieran los frameworks modernos, ya existía un problema muy real: cada navegador implementaba el DOM y los eventos de JavaScript de forma distinta, así que hacer algo tan simple como seleccionar un elemento y cambiarle una clase requería código diferente según el navegador. En 2006, John Resig lanzó jQuery para resolver justo eso: una sola API que funcionara igual en todos los navegadores.

🔌 Analogía: el adaptador universal

jQuery fue como esos adaptadores de corriente universales para viajar: no cambiaba lo que había del otro lado del enchufe (el navegador), pero te evitaba tener que cargar un adaptador distinto para cada país. Con una sola línea de jQuery lograbas algo que, sin él, te podía tomar varias líneas distintas según el navegador del usuario.

jQuery se volvió, por años, la librería de JavaScript más usada del planeta. Pero solo resolvía manipulación del DOM — no ayudaba a organizar aplicaciones grandes, con muchos estados y componentes interactuando entre sí. Ese fue el siguiente problema que la comunidad empezó a atacar.

💥
La explosión de las aplicaciones de una sola página (SPA)
2010-2013 — cuando la web dejó de ser solo documentos

A inicios de la década de 2010, sitios como Gmail y Facebook demostraron que un navegador podía comportarse casi como una aplicación de escritorio, cargando datos sin recargar la página completa. Esa idea —Single Page Application (SPA)— disparó la necesidad de herramientas más completas que jQuery.

Cada uno resolvía el problema de organizar aplicaciones grandes con una filosofía distinta: AngularJS traía un framework completo con muchas decisiones ya tomadas; React introdujo el concepto de componentes reutilizables y un DOM virtual para actualizar la pantalla de forma más eficiente; Vue buscó un punto intermedio, más fácil de adoptar poco a poco.

⚛️
React, Vue, y la carrera por reinventar la rueda
El auge del ecosistema npm aceleró todo

Cuando React demostró que el patrón de componentes y el DOM virtual funcionaban bien, muchos desarrolladores intentaron aplicar la misma idea con variaciones propias: mejor rendimiento, menos código repetitivo (boilerplate), o una curva de aprendizaje distinta. A esto se sumó el crecimiento de npm, el gestor de paquetes de Node.js, que hizo trivial publicar y compartir una librería nueva con el resto del mundo.

🟢 Por qué era tan fácil crear "uno más"

  • Publicar un paquete en npm no requiere aprobación de nadie, cualquiera puede hacerlo.
  • La comunidad de código abierto recompensaba (con estrellas en GitHub, atención en redes) a quien resolviera un problema de forma más elegante, aunque fuera marginal.
  • Cada nueva generación de herramientas de construcción (Grunt, Gulp, Webpack, Vite) también generaba su propia ola de frameworks compatibles con ella.
😩
La "fatiga de JavaScript" se vuelve un término oficial
2016 — cuando la propia comunidad empezó a quejarse en voz alta

Alrededor de 2016, el término "JavaScript fatigue" se popularizó en la comunidad de desarrollo, en buena parte gracias a artículos y publicaciones que describían la frustración de tener que aprender un stack completo nuevo —framework, herramienta de build, gestor de estado, librería de routing— cada vez que empezabas un proyecto, porque el "estándar de facto" del momento cambiaba con mucha frecuencia.

⚠️ No es solo percepción

Entre 2010 y 2016, la cantidad de herramientas nuevas de JavaScript publicadas en npm creció de forma exponencial. Aprender "JavaScript moderno" en ese periodo implicaba, en la práctica, elegir entre docenas de combinaciones posibles de framework, bundler y gestor de estado, sin que existiera todavía un camino claramente dominante.

🧭
Por qué sigue pasando hoy
Menos caos que en 2016, pero la máquina de crear frameworks no se detuvo
📦
npm
El gestor de paquetes de Node.js, que permite a cualquiera publicar y compartir código JavaScript reutilizable con enorme facilidad.
🌳
DOM virtual
Una representación en memoria de la interfaz que React popularizó, para calcular de forma eficiente qué partes de la pantalla realmente necesitan actualizarse.
🏗️
Bundler / herramienta de build
Software (como Webpack o Vite) que empaqueta y optimiza el código de un proyecto para que el navegador lo pueda cargar de forma eficiente.
🔁
Ciclo de innovación
El patrón repetido de que una idea nueva (componentes, DOM virtual, compilación en build-time) se vuelve popular y genera una nueva ronda de frameworks que la exploran desde distintos ángulos.

💡 Resumen del dato curioso

Los frameworks de JavaScript se multiplicaron porque el ecosistema es abierto, publicar herramientas nuevas es fácil, y cada generación de proyectos —jQuery, luego las primeras SPA, luego React y sus alternativas— resolvía un problema real de su momento. La "fatiga de JavaScript" no es solo una queja: refleja un ecosistema que, a diferencia de HTML o CSS, no depende de un único organismo de estandarización, sino de la comunidad decidiendo colectivamente, proyecto por proyecto, qué herramienta usar.
