Introducción — construir para todos, no solo para quien ve bien y usa mouse
Qué es la accesibilidad web y por qué no es "opcional"

La accesibilidad web (abreviada como a11y — la "11" cuenta las letras entre la "a" y la "y" de "accessibility") es el conjunto de prácticas que aseguran que una página funcione para personas con distintas capacidades: gente que usa lectores de pantalla, que navega solo con teclado, que tiene baja visión, o que usa un switch en lugar de un mouse.

💡 La idea central

Una página accesible no es una página "extra" para un grupo pequeño de usuarios — es una página construida sobre una base sólida de HTML semántico, donde cada elemento cumple el rol que dice cumplir. Cuando esa base es sólida, la mayoría de la accesibilidad viene gratis; ARIA existe para los casos donde el HTML nativo no alcanza.

🛗 Analogía: la rampa junto a la escalera

Una rampa de acceso no es solo para personas en silla de ruedas: también la usa quien lleva un carrito, una maleta o un coche de bebé. La accesibilidad web funciona igual: subtítulos que ayudan a alguien sordo también ayudan a quien mira un video sin sonido en el transporte público. Diseñar accesible casi siempre termina beneficiando a más personas de las que imaginabas al empezar.

Qué es ARIA
Accessible Rich Internet Applications

ARIA es un conjunto de atributos HTML que le dan información adicional a las tecnologías de asistencia (como lectores de pantalla) sobre elementos cuyo propósito no es evidente solo con HTML estándar — típicamente, componentes interactivos personalizados hechos con <div> o <span>.

⚠️ La primera regla de ARIA: "no uses ARIA"

Así lo dice literalmente la especificación oficial. Si existe una etiqueta HTML nativa que ya hace lo que necesitas —<button>, <nav>, <input>— úsala en vez de recrear su comportamiento con <div> y atributos ARIA. El HTML nativo ya trae accesibilidad, foco por teclado y semántica integrados; ARIA solo debería aparecer cuando construyes algo que el HTML no cubre.

Dicho esto, hay atributos ARIA muy comunes que sí vale la pena conocer:

<button aria-label="Cerrar ventana">✕</button> <!-- Le da nombre accesible a un botón que solo tiene un ícono --> <div role="alert"> El formulario tiene errores. </div> <!-- Anuncia el mensaje de inmediato al lector de pantalla --> <input aria-invalid="true" aria-describedby="err-email"> <span id="err-email">Correo inválido</span> <!-- Conecta un campo con su mensaje de error -->
AtributoPara qué sirve
aria-labelDa un nombre accesible a un elemento cuando no hay texto visible que lo describa.
aria-hiddenOculta un elemento decorativo (como un ícono) de los lectores de pantalla.
aria-expandedIndica si un menú, acordeón o desplegable está abierto o cerrado.
aria-liveAnuncia cambios dinámicos de contenido sin que el usuario tenga que buscar qué cambió.

Roles y landmarks: el mapa de la página
Cómo alguien que no ve la pantalla "ve" la estructura

Las personas que usan lectores de pantalla suelen navegar saltando entre regiones de la página, en vez de leerla de arriba a abajo. Las etiquetas HTML semánticas ya definen landmarks (puntos de referencia) automáticamente, sin necesitar ningún atributo ARIA extra.

<header>...</header> role="banner" implícito <nav>...</nav> role="navigation" implícito <main>...</main> role="main" implícito <aside>...</aside> role="complementary" implícito <footer>...</footer> role="contentinfo" implícito

🟢 Por qué esto importa tanto

  • Un lector de pantalla puede anunciar "hay 4 regiones: banner, navegación, principal, pie de página" y dejar que el usuario salte directo a la que le interese.
  • Si en cambio todo está hecho con <div>, no existe ese mapa — el usuario tiene que escuchar la página completa de corrido.
  • Usar <h1>-<h6> en orden lógico (sin saltarte niveles) le da al lector de pantalla otra forma rápida de navegar, saltando de encabezado en encabezado.

Navegación por teclado
Si no puedes usar tu sitio solo con Tab, alguien no podrá usarlo del todo

Mucha gente no usa mouse: por preferencia, por alguna discapacidad motriz, o porque usa un switch o un dispositivo de asistencia. Para esas personas, la tecla Tab (y Shift + Tab para retroceder) es la forma principal de moverse por la página.

TeclaQué debería pasar
TabMover el foco al siguiente elemento interactivo (enlace, botón, campo de formulario).
Shift + TabMover el foco al elemento interactivo anterior.
Enter / EspacioActivar un botón o enlace enfocado.
EscCerrar un modal o menú desplegable abierto.

⚠️ El error más común: quitar el "focus visible"

Es muy frecuente ver CSS como *:focus { outline: none; } aplicado para "limpiar" el diseño. El problema es que ese contorno (outline) es la única señal visual de dónde está el foco del teclado — quitarlo sin reemplazarlo por algo igual de visible deja a cualquier persona que navega por teclado completamente perdida en la página.

/* Mal: elimina la señal de foco sin reemplazo */ button:focus { outline: none; } /* Bien: reemplaza el outline por un estilo propio, igual de visible */ button:focus-visible { outline: 3px solid var(--primary); outline-offset: 2px; }

Otro elemento clave son los "skip links" (enlaces para saltar), un enlace oculto al inicio de la página que aparece al presionar Tab y permite saltar directo al contenido principal, sin tener que pasar tabulando por todo el menú de navegación en cada visita.

Buenas prácticas rápidas
Lo que más impacto tiene con menos esfuerzo
🖼️
alt en imágenes
Todo <img> con contenido informativo necesita un alt descriptivo. Si es puramente decorativa, usa alt="" para que el lector de pantalla la ignore.
🏷️
label en formularios
Cada <input> necesita un <label> asociado (con for/id), no solo un placeholder que desaparece al escribir.
🎨
Contraste de color
El texto necesita suficiente contraste contra su fondo — WCAG recomienda al menos 4.5:1 para texto normal.
🔘
button vs. div con onclick
Un <div onclick="..."> no recibe foco de teclado ni se activa con Enter por sí solo — un <button> sí, gratis.

Ejercicios
Para practicar lo que acabas de leer

Ejercicio 1 — Solo Tab

Escoge cualquier página que hayas construido en este curso. Guarda el mouse y navega usando solo Tab, Shift+Tab y Enter. Anota cada punto donde te "pierdas" o no sepas dónde está el foco.

Ejercicio 2 — Etiqueta ese botón

Busca en tu código algún ícono clickeable sin texto (una "X" para cerrar, una lupa de búsqueda). Agrégale un aria-label descriptivo, como aria-label="Cerrar ventana".

Ejercicio 3 — Audita con Lighthouse

Abre las DevTools de Chrome (F12), ve a la pestaña "Lighthouse", corre un análisis de accesibilidad sobre una página tuya, y corrige al menos dos de los problemas que reporte.

💡 Para llevarte de esta guía

La accesibilidad no es una capa que se agrega al final — la mayor parte se resuelve simplemente usando HTML semántico correctamente (<button>, <nav>, <label>) y probando que tu sitio funcione sin mouse. ARIA es la herramienta de refuerzo para los casos que el HTML nativo no cubre, no el punto de partida.
