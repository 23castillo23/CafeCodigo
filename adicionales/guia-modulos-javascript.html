Introducción — dividir el código sin que todo se pise entre sí
La forma estándar de organizar JavaScript en archivos separados

Conforme un proyecto crece, poner todo el JavaScript en un solo archivo se vuelve imposible de mantener. Los módulos de ES (ES Modules, o "ESM") son la forma estándar del propio lenguaje JavaScript para dividir el código en archivos separados que pueden compartir código entre sí de forma explícita y controlada.

💡 La idea central

Cada archivo de módulo tiene su propio espacio de variables, aislado del resto. Nada se comparte entre archivos a menos que lo exportes explícitamente desde un archivo, y lo importes explícitamente en otro.

📄
El problema que resuelven
Antes de los módulos, todo vivía en el mismo espacio global

Antes de que existieran los módulos nativos, incluir varios archivos <script> en una página significaba que todos compartían exactamente el mismo espacio de variables globales. Si dos archivos definían una variable o función con el mismo nombre, uno silenciosamente sobrescribía al otro.

<script src="a.js"></script> <script src="b.js"></script> <!-- Si ambos definen "function iniciar()", el de b.js gana --> <!-- y el orden de carga importa muchísimo -->

🏢 Analogía: la oficina de cubículos contra la oficina abierta

Sin módulos, es como si todos en una oficina compartieran un solo escritorio gigante: cualquiera puede mover o borrar las cosas de cualquier otro por accidente. Con módulos, cada quien tiene su propio cubículo (su propio archivo, con su propio espacio) — y si necesitas algo del cubículo vecino, tienes que pedirlo explícitamente, no simplemente tomarlo.

📤
export e import
Las dos palabras clave que hacen todo el trabajo
// matematicas.js export function sumar(a, b) { return a + b; } export function restar(a, b) { return a - b; } export const PI = 3.14159;
// app.js import { sumar, PI } from './matematicas.js'; console.log(sumar(2, 3)); // 5 console.log(PI); // 3.14159 // "restar" no se importó, así que no está disponible aquí

Cada archivo decide explícitamente qué comparte (con export) y cada archivo que lo usa decide explícitamente qué necesita de él (con import). Nada se filtra por accidente al espacio global.

🏷️
Named exports vs. default export
Dos formas distintas de exportar, cada una con su lugar
Named exportDefault export
Cantidad por archivoTantos como quierasSolo uno por archivo
Sintaxis al exportarexport function algo() {}export default function() {}
Sintaxis al importarimport { algo } from '...'import algo from '...'
Nombre al importarDebe coincidir con el original (o usar as)Puedes ponerle el nombre que quieras
// Boton.js — default export export default function Boton() { /* ... */ } // app.js — el nombre lo elige quien importa import MiBoton from './Boton.js'; // funciona igual import BotonComoSea from './Boton.js'; // también funciona

🟢 Cuándo usar cada uno

  • Named exports: cuando un archivo exporta varias utilidades relacionadas (funciones matemáticas, helpers de fecha).
  • Default export: cuando el archivo representa "una sola cosa principal" — típico en componentes de interfaz, uno por archivo.
  • También puedes combinar ambos en el mismo archivo si tiene sentido para tu caso.
🌐
Usarlos directo en el navegador
Sin necesitar ninguna herramienta de build

Los navegadores modernos soportan módulos de forma nativa. Solo hace falta agregar type="module" al <script>:

<script type="module" src="app.js"></script>
DiferenciaCon type="module"Script normal
Alcance de variablesAisladas al móduloGlobales, compartidas entre scripts
Modo estrictoActivado automáticamenteHay que escribir 'use strict' manualmente
CargaSiempre diferida (como defer)Bloquea el parsing salvo que uses defer/async
import/exportDisponiblesNo disponibles — error de sintaxis

⚠️ Con file:// (abrir el HTML directo) suele fallar

Los módulos requieren que la página se sirva por HTTP (aunque sea local, con algo como python -m http.server o Live Server), por restricciones de seguridad del navegador (CORS). Abrir el archivo HTML directamente con doble clic suele lanzar un error de módulos bloqueados.

📦
Un módulo, una responsabilidad
Cada archivo debería tener un propósito claro y acotado — evita archivos "utils.js" gigantes con cien funciones sin relación entre sí.
🚪
Archivo de entrada claro
Un archivo principal (como app.js o main.js) que importa y coordina a los demás, en vez de que cualquier archivo importe de cualquier otro sin orden.
🔁
Evita dependencias circulares
Si el archivo A importa de B, y B importa de A, puedes obtener valores undefined inesperados — reorganiza el código para que la dependencia vaya en una sola dirección.
🏷️
Nombres de archivo descriptivos
El nombre del archivo debería anticipar qué exporta — validaciones-formulario.js es más útil que helpers2.js.

Ejercicios
Para practicar lo que acabas de leer

Ejercicio 1 — Tu primer módulo

Crea un archivo saludos.js con dos funciones exportadas: saludar(nombre) y despedir(nombre). Impórtalas en un app.js y úsalas ahí.

Ejercicio 2 — Default export

Convierte una de esas dos funciones en el export default de un archivo separado, e impórtala con un nombre distinto al original para comprobar que funciona igual.

Ejercicio 3 — Sírvelo por HTTP

Abre tu archivo con type="module" directamente con doble clic (file://) y observa el error en consola. Luego sírvelo con un servidor local simple (como la extensión Live Server) y comprueba que ahora sí funciona.

💡 Para llevarte de esta guía

Los ES Modules son la forma nativa del lenguaje para dividir código en archivos con su propio espacio aislado, compartiendo solo lo que se exporta explícitamente. Requieren type="module" y servirse por HTTP — pero a cambio, eliminan por completo los problemas de variables globales chocando entre sí.
