Introducción — pedirle datos a un servidor sin congelar la página
La base de casi cualquier app web moderna

Casi ninguna aplicación web real trabaja solo con datos que ya tiene: necesita pedirle información a un servidor —una API de clima, una base de datos de productos, un backend propio— y mostrarla en pantalla. La Fetch API es la forma estándar y moderna de hacer esas peticiones en JavaScript, y trabaja de la mano con las promesas.

💡 La idea central

Una petición de red tarda un tiempo indeterminado en responder. JavaScript no se queda "congelado" esperando: sigue ejecutando el resto del código, y usa una promesa como recibo que representa "aquí llegará un resultado, tarde o temprano" — para bien (los datos) o para mal (un error).

🎟️
Qué es una promesa
Un objeto con tres posibles estados

🎫 Analogía: el boleto del restaurante

Cuando pides comida para llevar, te dan un número de orden. Ese número no es la comida —es una promesa de que la comida llegará—. Mientras esperas, puedes hacer otras cosas. Cuando te llaman, pasa una de dos cosas: te entregan tu pedido (promesa cumplida) o te avisan que se acabó el platillo que pediste (promesa rechazada). Una promesa de JavaScript funciona exactamente igual.

pending

Toda promesa nace en estado pending y termina en exactamente uno de los otros dos estados, nunca en ambos, y nunca puede volver a cambiar una vez resuelta.

🌐
fetch() paso a paso
La forma clásica, encadenando .then()
fetch('https://api.ejemplo.com/usuarios') .then(respuesta => respuesta.json()) // convierte el body a JSON .then(datos => { console.log(datos); }) .catch(error => { console.error('Algo salió mal:', error); });

fetch() devuelve una promesa que se resuelve con un objeto Response — pero ese objeto todavía no es tus datos, es un contenedor. Por eso el primer .then() casi siempre llama a .json() (u otro método como .text()), que a su vez devuelve otra promesa con los datos ya listos para usar.

⚠️ El error que casi todo mundo comete al inicio

fetch() no rechaza la promesa ante errores HTTP como 404 o 500 — solo la rechaza si hay un problema de red (sin conexión, dominio inexistente). Hay que revisar manualmente respuesta.ok o respuesta.status para detectar esos casos, como se muestra más abajo.

✨
async/await: la forma moderna
Código asíncrono que se lee como si fuera síncrono

async/await es "azúcar sintáctica" sobre las promesas: no reemplaza nada por debajo, pero permite escribir el mismo código de forma mucho más lineal y fácil de leer.

async function obtenerUsuarios() { const respuesta = await fetch('https://api.ejemplo.com/usuarios'); const datos = await respuesta.json(); console.log(datos); } obtenerUsuarios();

🟢 Dato clave: await no bloquea el navegador

Aunque await "pausa" la función hasta que la promesa se resuelve, el resto de la página sigue respondiendo — solo se pausa la ejecución de esa función específica, no el navegador completo.

🚨
Manejo de errores
Cubriendo tanto errores de red como errores HTTP
async function obtenerUsuarios() { try { const respuesta = await fetch('https://api.ejemplo.com/usuarios'); if (!respuesta.ok) { throw new Error(`Error HTTP: ${respuesta.status}`); } const datos = await respuesta.json(); return datos; } catch (error) { console.error('No se pudo obtener a los usuarios:', error.message); // aquí podrías mostrar un mensaje al usuario } }

Un try/catch bien hecho para fetch() debe cubrir dos tipos de fallo distintos: errores de red (sin conexión, dominio caído — estos sí rechazan la promesa automáticamente) y errores HTTP (404, 500 — que hay que detectar manualmente revisando respuesta.ok).

🔀
Peticiones en paralelo con Promise.all()
Cuando necesitas varias respuestas al mismo tiempo, no una tras otra
async function cargarTodo() { const [usuarios, productos] = await Promise.all([ fetch('/api/usuarios').then(r => r.json()), fetch('/api/productos').then(r => r.json()) ]); console.log(usuarios, productos); }

⚠️ Un await tras otro es más lento de lo necesario

Si escribes dos await fetch(...) seguidos sin Promise.all(), la segunda petición ni siquiera empieza hasta que la primera termine por completo — desperdiciando tiempo cuando ambas peticiones no dependen entre sí. Promise.all() las lanza a todas al mismo tiempo y espera a que todas terminen.

MétodoComportamiento
Promise.all()Espera a todas; si UNA falla, rechaza todo el conjunto de inmediato.
Promise.allSettled()Espera a todas y siempre resuelve, indicando cuáles tuvieron éxito y cuáles fallaron.
Promise.race()Se resuelve o rechaza tan pronto como la primera promesa del grupo termine.

Ejercicios
Para practicar lo que acabas de leer

Ejercicio 1 — Tu primer fetch

Usa fetch('https://jsonplaceholder.typicode.com/users') para traer una lista de usuarios de prueba y muéstralos en la consola usando async/await.

Ejercicio 2 — Maneja el error

Modifica tu código anterior para pedir una URL que no existe (agrega letras random al final) y verifica que tu try/catch capture el error correctamente sin romper la página.

Ejercicio 3 — Dos peticiones en paralelo

Usa Promise.all() para pedir al mismo tiempo /users y /posts de jsonplaceholder.typicode.com, y muestra cuántos elementos trajo cada una.

💡 Para llevarte de esta guía

Las promesas son el mecanismo, fetch() es la herramienta, y async/await es la forma más legible de usarlas juntas. Recuerda siempre revisar respuesta.ok — fetch() no te avisa solo de los errores HTTP — y usa Promise.all() quien necesite varias peticiones que no dependen entre sí.
