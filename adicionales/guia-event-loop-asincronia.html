Introducción — un solo hilo, muchas cosas "al mismo tiempo"
Cómo JavaScript logra parecer multitarea sin serlo

JavaScript ejecuta código en un solo hilo: solo puede hacer una cosa a la vez, literalmente. Y sin embargo, todos los días ves páginas que cargan imágenes, esperan respuestas de servidor y animan cosas, todo aparentemente "al mismo tiempo". El mecanismo que hace posible esa ilusión se llama event loop (bucle de eventos).

💡 La idea central

JavaScript no espera nunca de brazos cruzados. Cuando encuentra una tarea que tomará tiempo (un setTimeout, una petición fetch), se la delega al navegador y sigue ejecutando el resto del código. El event loop es el mecanismo que, más tarde, trae de vuelta el resultado de esa tarea para ejecutarlo, en el momento correcto.

📚
El call stack (pila de llamadas)
Donde vive el código que se está ejecutando ahora mismo

El call stack es una estructura donde JavaScript apila las funciones que está ejecutando, una encima de otra. Cuando una función termina, se "desapila" (pop), y el control regresa a quien la llamó.

function multiplicar(a, b) { return a * b; } function calcularArea(ancho, alto) { return multiplicar(ancho, alto); } console.log(calcularArea(4, 5)); // 20

🍽️ Analogía: la torre de platos sucios

El call stack es como una torre de platos: solo puedes lavar el plato de hasta arriba. calcularArea() se apila, y dentro de ella se apila multiplicar() encima. Primero se "lava" (termina) multiplicar(), y solo entonces puede terminar calcularArea() debajo de ella.

⚠️ Si el stack nunca se vacía, la página se congela

Como JavaScript es de un solo hilo, mientras el call stack tenga algo ejecutándose, nada más puede pasar — ni clics, ni animaciones, ni el event loop. Un bucle infinito o un cálculo muy pesado sin pausas bloquea la página entera. Por eso operaciones costosas suelen dividirse o delegarse a Web Workers.

🌐
Web APIs: dónde "esperan" las tareas
setTimeout y fetch no los ejecuta JavaScript directamente

Funciones como setTimeout(), fetch() o los listeners de eventos del DOM no las maneja el motor de JavaScript por sí solo — se las delega al navegador (o a Node.js, en el caso del servidor), que las ejecuta por fuera del hilo principal y avisa cuando terminan.

console.log('1'); setTimeout(() => { console.log('2'); }, 0); console.log('3'); // Resultado en consola: // 1 // 3 // 2

Aunque el setTimeout tenga 0 milisegundos, "2" se imprime al final. El navegador toma el callback y lo pone en espera; el event loop solo lo trae de vuelta al call stack cuando este ya está completamente vacío — nunca antes, sin importar qué tan corto sea el tiempo indicado.

📥
Dos colas: microtasks y macrotasks
No todas las tareas pendientes tienen la misma prioridad

Cuando una tarea delegada termina, no vuelve al call stack de cualquier forma: entra a una de dos colas, y el event loop las trata con distinta prioridad.

1. Call stackSe vacía por completo antes de tocar cualquier cola.
↓ una vez vacío, revisa primero...
2. Cola de microtasksPromesas (.then, async/await), queueMicrotask(). Se vacía POR COMPLETO antes de seguir.
↓ solo cuando la cola de microtasks está vacía...
3. Cola de macrotaskssetTimeout, setInterval, eventos de UI. Se ejecuta UNA sola, y se vuelve al paso 2.
Van a la cola de microtasksVan a la cola de macrotasks
.then() / .catch() de promesassetTimeout() / setInterval()
async/await (por debajo, son promesas)Eventos del DOM (clics, scroll)
queueMicrotask()setImmediate() (en Node.js)

🟢 La regla que explica el 90% de las sorpresas

Las microtasks siempre se ejecutan antes que la siguiente macrotask, sin importar el orden en que se hayan agregado. Por eso una promesa resuelta "instantáneamente" siempre se ejecuta antes que un setTimeout(fn, 0), aunque ambos parezcan estar "listos" al mismo tiempo.

🔍
Un ejemplo, línea por línea
El clásico que confunde a todo mundo la primera vez
console.log('A'); setTimeout(() => console.log('B'), 0); Promise.resolve().then(() => console.log('C')); console.log('D'); // Resultado en consola: // A // D // C // B
  1. A y D se ejecutan de inmediato — son código síncrono en el call stack.
  2. setTimeout manda su callback a la cola de macrotasks; Promise.resolve().then() manda el suyo a la cola de microtasks.
  3. Cuando el call stack queda vacío (después de D), el event loop revisa primero la cola de microtasks: por eso C sale antes que B.
  4. Solo cuando la cola de microtasks está vacía, se procesa una macrotask: por eso B es el último.

Ejercicios
Para practicar lo que acabas de leer

Ejercicio 1 — Predice el orden

Antes de correrlo, escribe en papel el orden que crees que imprimirá este código, y después verifícalo:

console.log('uno'); setTimeout(() => console.log('dos'), 0); setTimeout(() => console.log('tres'), 0); Promise.resolve().then(() => console.log('cuatro')); console.log('cinco');

Ejercicio 2 — Bloquea y observa

Escribe un setTimeout de 0ms, y justo después un bucle for vacío que corra 500 millones de veces. Observa cómo el setTimeout no se ejecuta "casi al instante" como esperarías — tiene que esperar a que el bucle termine de bloquear el call stack.

Ejercicio 3 — Dos promesas encadenadas

Encadena tres .then() sobre una promesa ya resuelta, con un setTimeout intercalado entre ellos en el código. Observa cómo las tres microtasks se procesan antes que el setTimeout, aunque este se haya escrito primero.

💡 Para llevarte de esta guía

JavaScript es de un solo hilo, pero delega tareas lentas al navegador y las recupera con el event loop, siempre respetando este orden: primero vacía el call stack, luego TODA la cola de microtasks, y solo entonces procesa una macrotask a la vez. Entender esta jerarquía explica prácticamente cualquier "sorpresa" de orden de ejecución que encuentres con promesas y timers.
