Introducción — un sitio web que sigue funcionando sin internet
La tecnología detrás de las Progressive Web Apps (PWA)

Una PWA (Progressive Web App) es un sitio web que puede comportarse como una aplicación instalable: funciona sin conexión, se agrega a la pantalla de inicio, y puede enviar notificaciones — todo construido con HTML, CSS y JavaScript, sin necesitar las tiendas de aplicaciones. La pieza central que hace esto posible es el Service Worker.

💡 La idea central

Un Service Worker es un script que el navegador ejecuta por separado de tu página, actuando como un intermediario (proxy) entre tu sitio y la red. Puede interceptar cada petición de red que hace tu página y decidir: responder con algo guardado en caché, ir a buscarlo a internet, o una combinación de ambos.

⚙️
Qué es un Service Worker
Un script con vida propia, separado de tu página

🚪 Analogía: el portero del edificio

Un Service Worker es como el portero de un edificio de oficinas: toda visita (petición de red) pasa primero por él. El portero puede dejarte pasar directo (ir a la red), decirte "espera, tengo una copia de eso guardada aquí mismo" (responder desde caché), o incluso decirte "no hay servicio ahora mismo, pero aquí tienes una versión guardada de todos modos" (funcionar offline).

CaracterísticaDetalle
Corre en un hilo separadoNo tiene acceso directo al DOM y no bloquea la interfaz de tu página.
Sigue vivo sin la pestaña abiertaPuede seguir ejecutándose (por ejemplo, para notificaciones push) aunque hayas cerrado la pestaña.

// sw.js — el archivo del propio Service Worker const CACHE_NAME = 'cafe-codigo-v1'; self.addEventListener('install', (evento) => { evento.waitUntil( caches.open(CACHE_NAME).then(cache => { return cache.addAll([ '/', '/estilos.css', '/app.js' ]); }) ); }); self.addEventListener('activate', (evento) => { console.log('Service Worker activado'); });

⚠️ El primer registro NO controla la página que lo registró

La primera vez que un Service Worker se instala, la página que provocó el registro sigue cargando de forma normal, sin pasar por él — solo empieza a controlar peticiones desde la siguiente carga de página. Esto evita comportamientos inesperados en la primera visita.

📦
Cache API
Un almacén de respuestas HTTP completas, no solo texto

A diferencia de localStorage (que solo guarda texto), la Cache API almacena objetos Request/Response completos — el equivalente a guardar copias reales de páginas, imágenes o archivos, no solo datos.

self.addEventListener('fetch', (evento) => { evento.respondWith( caches.match(evento.request).then(respuestaCache => { // Si está en caché, úsala. Si no, ve a la red. return respuestaCache || fetch(evento.request); }) ); });

El evento fetch se dispara para cada petición que hace la página (HTML, CSS, JS, imágenes, llamadas a API) mientras el Service Worker está activo — y evento.respondWith() es lo que te permite decidir qué responder en su lugar.

EstrategiaMejor para
Cache FirstRecursos que casi nunca cambian: fuentes, íconos, CSS/JS con versión en el nombre del archivo.
Network FirstContenido que debe estar actualizado si hay conexión, pero puede mostrar una versión vieja si no la hay: noticias, precios.
Stale-While-RevalidateUn balance entre velocidad y frescura: responde rápido con lo que ya tienes, y actualiza la caché en segundo plano para la próxima vez.

🟢 No existe una estrategia "correcta" universal

La mejor estrategia depende de cada tipo de recurso dentro del mismo sitio — es común combinar varias en un mismo Service Worker, según la ruta o el tipo de archivo que se esté pidiendo.

📱
El manifest.json
Lo que convierte "un sitio con Service Worker" en "algo instalable"

El Service Worker resuelve el funcionamiento offline, pero para que el navegador ofrezca "Instalar aplicación" (agregarla a la pantalla de inicio, con ícono propio), también se necesita un archivo manifest.json enlazado desde el HTML.

// manifest.json { "name": "Café </>", "short_name": "Café", "start_url": "/", "display": "standalone", "background_color": "#1a1814", "theme_color": "#c49a1a", "icons": [ { "src": "/icono-192.png", "sizes": "192x192", "type": "image/png" }, { "src": "/icono-512.png", "sizes": "512x512", "type": "image/png" } ] }
<link rel="manifest" href="/manifest.json">

Ejercicios
Para practicar lo que acabas de leer

Ejercicio 1 — Registra tu primer Service Worker

Crea un sw.js vacío (solo con un console.log('activo') en el evento activate) y regístralo desde tu app.js. Verifica en el panel Application de las DevTools que aparezca como activo.

Ejercicio 2 — Cachea tu página principal

En el evento install, guarda tu index.html, tu CSS y tu JS en caché. Desconéctate de internet (o usa "Offline" en el panel Network de DevTools) y recarga la página — debería seguir funcionando.

Ejercicio 3 — Crea un manifest.json

Escribe tu propio manifest.json con nombre, colores e íconos, enlázalo desde tu HTML, y comprueba en Chrome que aparece la opción de "Instalar" en la barra de direcciones.

💡 Para llevarte de esta guía

Un Service Worker es un proxy programable entre tu página y la red, que junto con la Cache API permite decidir exactamente cómo responder a cada petición — incluso sin conexión. El manifest.json es lo que completa la experiencia, permitiendo que el navegador ofrezca instalar tu sitio como si fuera una aplicación nativa.
