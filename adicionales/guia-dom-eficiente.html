Introducción — el DOM es más lento de lo que parece
Por qué "funciona" no siempre significa "funciona bien"

Es fácil escribir código que manipula el DOM y que "funciona" en pruebas pequeñas, pero que se vuelve notablemente lento con listas grandes o interacciones frecuentes. La razón casi siempre es la misma: cada cambio al DOM puede obligar al navegador a recalcular estilos y posiciones — un trabajo que no es gratis.

💡 La idea central

El DOM no es una simple estructura de datos en memoria — es una API conectada directamente al motor de renderizado del navegador. Cada lectura o escritura puede disparar trabajo adicional invisible. Escribir DOM eficiente significa minimizar cuántas veces provocas ese trabajo, no cuántas líneas de código escribes.

🔄
Reflow y repaint: los dos costos ocultos
No todos los cambios al DOM cuestan lo mismo
Tipo de cambioQué provocaCosto
Reflow (layout)Cambiar tamaño, posición o estructura (agregar/quitar elementos, cambiar width).Alto — recalcula posiciones de potencialmente toda la página.
RepaintCambiar apariencia sin afectar layout (color, background).Medio — repinta píxeles, sin recalcular posiciones.
Compositetransform, opacity.Bajo — se maneja en la GPU, sin tocar layout ni pintura.

🏗️ Analogía: mover un mueble contra pintar una pared

Un reflow es como mover un mueble grande en una casa ya amueblada: puede obligarte a reacomodar todo lo demás para que quepa. Un repaint es como pintar una pared de otro color: no hay que mover nada, solo cambia la apariencia. Un cambio con transform es como poner un cuadro flotante frente a la pared, sin tocarla en absoluto — el más barato de los tres.

⚠️ Leer y escribir intercalado es el peor patrón

Alternar entre leer una propiedad que depende del layout (como elemento.offsetHeight) y escribir estilos, dentro de un bucle, fuerza al navegador a recalcular el layout en cada iteración en lugar de una sola vez — un problema conocido como "layout thrashing".

📦
DocumentFragment: construir fuera, insertar una sola vez
Evita insertar al DOM real dentro de un bucle
// ❌ Ineficiente: modifica el DOM real 100 veces for (let i = 0; i < 100; i++) { const li = document.createElement('li'); li.textContent = `Elemento ${i}`; lista.appendChild(li); // posible reflow en cada vuelta } // ✅ Eficiente: construye todo en memoria, inserta una sola vez const fragmento = document.createDocumentFragment(); for (let i = 0; i < 100; i++) { const li = document.createElement('li'); li.textContent = `Elemento ${i}`; fragmento.appendChild(li); // esto NO toca el DOM real todavía } lista.appendChild(fragmento); // un solo reflow, al final

    Delegación de eventos
    Un solo listener en vez de cientos

    Agregar un addEventListener individual a cada elemento de una lista larga consume memoria y tiempo de configuración innecesarios. La delegación de eventos aprovecha que los eventos "burbujean" (se propagan) hacia arriba en el DOM, permitiendo escuchar en un solo elemento padre.

    // ❌ Ineficiente: un listener por cada <li> document.querySelectorAll('li').forEach(li => { li.addEventListener('click', () => console.log(li.textContent)); }); // ✅ Eficiente: UN listener en el contenedor padre lista.addEventListener('click', (evento) => { if (evento.target.tagName === 'LI') { console.log(evento.target.textContent); } });

    🟢 Ventaja extra: funciona con elementos agregados después

    Como el listener vive en el contenedor padre (que ya existe), cualquier <li> que agregues después —incluso dinámicamente— también dispara el evento correctamente, sin necesitar agregarle un listener nuevo cada vez.

    📚
    Agrupar lecturas y escrituras
    Separa "leer" de "escribir" en fases distintas
    // ❌ Ineficiente: alterna lectura y escritura, provoca layout thrashing cajas.forEach(caja => { const altura = caja.offsetHeight; // LEE (fuerza layout) caja.style.height = altura * 2 + 'px'; // ESCRIBE }); // ✅ Eficiente: primero lee TODO, luego escribe TODO const alturas = cajas.map(caja => caja.offsetHeight); // una sola fase de lectura cajas.forEach((caja, i) => { caja.style.height = alturas[i] * 2 + 'px'; // una sola fase de escritura });

    Al separar todas las lecturas en un bloque y todas las escrituras en otro, el navegador solo necesita recalcular el layout una vez para todo el conjunto, en vez de una vez por cada elemento del bucle.

    📖
    Propiedades que fuerzan layout al leerse
    offsetHeight, offsetWidth, getBoundingClientRect(), scrollTop, entre otras — todas obligan al navegador a calcular el layout actual antes de responder.
    ✍️
    Cambios que "ensucian" el layout
    Modificar style, agregar/quitar clases o elementos, cambiar innerHTML — marcan el layout como desactualizado.
    🏋️
    Ejercicios
    Para practicar lo que acabas de leer

    Ejercicio 1 — Usa un fragmento

    Toma un bucle que inserte 50 elementos directo a una lista con appendChild uno por uno, y reescríbelo usando DocumentFragment para que solo haya una inserción real al DOM.

    Ejercicio 2 — Delega un click

    Crea una lista de 10 elementos con un solo addEventListener('click') en el <ul> padre, que identifique cuál <li> fue clickeado usando evento.target.

    Ejercicio 3 — Encuentra el layout thrashing

    Escribe un bucle que alterne offsetWidth (lectura) con cambios de style.width (escritura) sobre 20 elementos. Luego reescríbelo separando la fase de lectura de la de escritura.

    💡 Para llevarte de esta guía

    El DOM es rápido si lo tratas con cuidado: agrupa inserciones con DocumentFragment, usa delegación de eventos en vez de un listener por elemento, y separa tus lecturas de tus escrituras para evitar layout thrashing. Ninguna de estas técnicas cambia lo que tu código hace — solo cuántas veces obligas al navegador a recalcular las cosas.
