Principios de seguridad en Linux
Los fundamentos que guían todas las decisiones de seguridad

La seguridad en Linux no es un producto que instalas — es una práctica continua basada en principios. Entenderlos te permite tomar buenas decisiones de seguridad en situaciones nuevas, no solo aplicar recetas.

🎯
Principio de mínimo privilegio
Cada proceso, usuario y servicio debe tener solo los permisos estrictamente necesarios para su función. Nada más. Un servidor web no necesita acceso a /home. Un script de backup no necesita sudo.
🔒
Defensa en profundidad
No confíes en una sola capa de seguridad. Usa múltiples capas: firewall + autenticación por clave + fail2ban + actualizaciones + auditoría. Si una falla, las otras siguen protegiendo.
📦
Reducir la superficie de ataque
Cada servicio que no necesitas es una puerta de entrada potencial. Desinstala software innecesario. Cierra puertos que no uses. Deshabilita servicios que no necesitas.
🔄
Mantener el sistema actualizado
La mayoría de los ataques explotan vulnerabilidades conocidas con parches disponibles. Actualizar regularmente es la medida de seguridad con mejor relación esfuerzo/resultado.
📋
Auditar y monitorizar
Lo que no se monitoriza, no se detecta. Los logs son tu fuente de verdad. Revisa auth.log regularmente. Configura alertas. Asume que intentarán entrar — prepárate para detectarlo.

🏰 Analogía — El castillo medieval

Un sistema Linux seguro es como un castillo: tiene un foso (firewall — impide llegar a las puertas), puertas con guardia (SSH con claves — solo entran los autorizados), vigilantes en las torres (fail2ban — detectan ataques repetidos), diferentes salas con llave (permisos — cada habitante accede solo a su área) y un libro de visitas (logs de auditoría — queda registro de todo). Si una puerta cede, las demás siguen protegiendo.

🔄
Actualizaciones de seguridad
La medida de seguridad más impactante y más fácil de implementar

La inmensa mayoría de los compromisos exitosos explotan vulnerabilidades conocidas para las que ya existe un parche. Mantener el sistema actualizado cierra esas puertas antes de que los atacantes las encuentren.

actualizaciones manuales y automáticas
# Actualización completa manual (Debian/Ubuntu) $ sudo apt update && sudo apt upgrade -y && sudo apt autoremove -y # Ver qué actualizaciones de seguridad hay disponibles $ sudo apt list --upgradable 2>/dev/null | grep -i security # unattended-upgrades — instalar automáticamente parches de seguridad $ sudo apt install unattended-upgrades $ sudo dpkg-reconfigure --priority=low unattended-upgrades # Activa la descarga e instalación automática de parches de seguridad # Ver configuración de unattended-upgrades $ cat /etc/apt/apt.conf.d/50unattended-upgrades | grep -v "^//\|^$" # Ver historial de actualizaciones aplicadas $ cat /var/log/unattended-upgrades/unattended-upgrades.log | tail -20 # Verificar si el sistema necesita reiniciar tras una actualización $ ls /var/run/reboot-required 2>/dev/null && echo "REINICIO NECESARIO" || echo "OK" # needrestart — detectar servicios que necesitan reiniciarse $ sudo apt install needrestart $ sudo needrestart

🟢 Actualizar el kernel requiere reiniciar

Las actualizaciones de paquetes normales se aplican inmediatamente sin reiniciar. Las actualizaciones del kernel requieren reiniciar para que el nuevo kernel entre en efecto. Puedes verificar si hay un reinicio pendiente con ls /var/run/reboot-required. En servidores críticos, planifica ventanas de mantenimiento para los reinicios.

sudo seguro — mínimo privilegio en práctica
Configurar sudo correctamente para limitar el daño potencial
sudo — buenas prácticas de seguridad
# Ver el log de sudo — quién usó sudo y qué ejecutó $ sudo cat /var/log/auth.log | grep sudo | tail -20 jan 15 10:23:45 ubuntu sudo: hugo : TTY=pts/0 ; COMMAND=/usr/bin/apt update jan 15 10:24:01 ubuntu sudo: hugo : TTY=pts/0 ; COMMAND=/usr/bin/apt upgrade # Limitar lo que puede hacer un usuario con sudo (en /etc/sudoers via visudo) # Ejemplo: el usuario 'deploy' solo puede reiniciar nginx y node $ sudo visudo # Añadir: # deploy ALL=(ALL) NOPASSWD: /bin/systemctl restart nginx, /bin/systemctl restart node-app # Reducir el timeout de sudo (por defecto 15 minutos) # En /etc/sudoers: # Defaults timestamp_timeout=5 → pide contraseña cada 5 minutos # Defaults timestamp_timeout=0 → pide contraseña cada vez # Ver qué usuarios tienen acceso sudo $ grep -E '^sudo' /etc/group sudo:x:27:hugo # Ver todos los archivos de sudoers $ ls /etc/sudoers.d/ # Revocar acceso sudo a un usuario $ sudo gpasswd -d usuario sudo # Invalidar el caché de sudo (obliga a pedir contraseña de nuevo) $ sudo -k

⚠️ NOPASSWD — con moderación

NOPASSWD en sudoers permite ejecutar comandos como root sin contraseña. Es útil para scripts de despliegue automático, pero peligroso si se abusa: cualquier proceso que se ejecute como ese usuario puede escalar a root sin barreras. Úsalo solo para comandos específicos y bien delimitados, nunca para ALL.

SSH seguro — endurecer el acceso remoto
Las configuraciones de sshd_config que cierran las puertas más comunes
# /etc/ssh/sshd_config — configuración de seguridad recomendada # 1. Deshabilitar login como root directamente PermitRootLogin no # 2. Deshabilitar autenticación por contraseña (solo claves) PasswordAuthentication no ChallengeResponseAuthentication no # 3. Cambiar el puerto por defecto (reduce el ruido de bots) Port 2222 # cambia el 22 a otro número # 4. Limitar los usuarios que pueden hacer SSH AllowUsers hugo deploy # 5. Limitar los intentos de autenticación MaxAuthTries 3 # 6. Desconectar sesiones inactivas ClientAliveInterval 300 ClientAliveCountMax 2 # 7. Usar solo protocolo SSH v2 (v1 tiene vulnerabilidades conocidas) Protocol 2 # Después de editar, validar la configuración y reiniciar # $ sudo sshd -t && sudo systemctl restart sshd
SSHD_CONFIG
aplicar y verificar la configuración SSH
# Validar la configuración antes de reiniciar (evita quedar sin acceso) $ sudo sshd -t # Si no da error → la configuración es válida # Reiniciar SSH con la nueva configuración $ sudo systemctl restart sshd # Ver intentos de login fallidos (ataques de fuerza bruta) $ sudo grep "Failed password" /var/log/auth.log | tail -20 jan 15 03:45:12 ubuntu sshd: Failed password for root from 185.234.218.47 jan 15 03:45:14 ubuntu sshd: Failed password for root from 185.234.218.47 # Ver las IPs que más intentan entrar $ sudo grep "Failed password" /var/log/auth.log | awk '{print $11}' | sort | uniq -c | sort -rn | head -10 # Ver logins exitosos $ sudo grep "Accepted" /var/log/auth.log | tail -10 jan 15 10:30:22 ubuntu sshd: Accepted publickey for hugo from 192.168.1.50

💡 El orden de operaciones para endurecer SSH

Hay un orden crítico al endurecer SSH: primero genera y copia las claves SSH, verifica que puedes conectarte sin contraseña, y SOLO ENTONCES desactiva PasswordAuthentication. Si lo haces al revés y algo falla con las claves, te quedas sin acceso al servidor. Mantén siempre una segunda sesión SSH abierta mientras haces cambios para poder revertir si algo sale mal.

UFW — firewall sencillo para Linux
Uncomplicated Firewall — la interfaz amigable sobre iptables

UFW (Uncomplicated Firewall) es la interfaz más amigable para gestionar el firewall de Linux. Por debajo usa iptables o nftables, pero con una sintaxis legible y sencilla. Es el estándar en Ubuntu y Debian.

🚨 Analogía — El portero del club

UFW es el portero de tu servidor. Tiene una lista de quién puede entrar (reglas ALLOW) y una lista negra (reglas DENY). Por defecto, el portero es muy restrictivo: nadie entra a menos que esté en la lista blanca. Tú defines las reglas: "dejar pasar solo por las puertas 22 (SSH), 80 (web) y 443 (web segura) — las demás puertas permanecen cerradas".

UFW — instalación, configuración y reglas
## INSTALACIÓN Y ACTIVACIÓN $ sudo apt install ufw # ANTES de activar, permite SSH para no quedarte bloqueado $ sudo ufw allow ssh # = allow 22/tcp $ sudo ufw enable # activa el firewall Command may disrupt existing ssh connections. Proceed with operation (y|n)? y Firewall is active and enabled on system startup ## VER ESTADO Y REGLAS $ sudo ufw status verbose Status: active Default: deny (incoming), allow (outgoing), disabled (routed) To Action From 22/tcp ALLOW IN Anywhere 80/tcp ALLOW IN Anywhere 443/tcp ALLOW IN Anywhere ## AÑADIR REGLAS $ sudo ufw allow 80/tcp # HTTP $ sudo ufw allow 443/tcp # HTTPS $ sudo ufw allow 'Nginx Full' # perfil de app (80 + 443) $ sudo ufw allow from 192.168.1.0/24 to any port 5432 # PostgreSQL solo LAN $ sudo ufw deny 3306 # bloquear MySQL desde el exterior ## ELIMINAR REGLAS $ sudo ufw status numbered # ver reglas numeradas $ sudo ufw delete 3 # eliminar regla número 3 $ sudo ufw delete allow 80/tcp # eliminar por nombre ## LIMITAR UN PUERTO (protección básica anti-bruteforce) $ sudo ufw limit ssh # bloquea IP tras 6 intentos en 30s ## DESACTIVAR Y RESETEAR $ sudo ufw disable # desactivar el firewall $ sudo ufw reset # eliminar todas las reglas
ALLOW 22/tcp (SSH) — acceso remoto a administración
ALLOW 80/tcp (HTTP) — servidor web
ALLOW 443/tcp (HTTPS) — servidor web seguro
DENY 3306/tcp (MySQL) — base de datos solo accesible localmente
DENY Todo lo demás — política por defecto: deny incoming

fail2ban — banear IPs atacantes automáticamente
Detección de ataques de fuerza bruta y bloqueo automático

fail2ban monitoriza los logs del sistema en tiempo real. Cuando detecta un número excesivo de intentos fallidos de autenticación desde una IP, la bloquea automáticamente con iptables/UFW durante un tiempo configurable.

fail2ban — instalación y configuración
# Instalar fail2ban $ sudo apt install fail2ban $ sudo systemctl enable --now fail2ban # Crear configuración personalizada (NUNCA editar jail.conf directamente) $ sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local $ sudo nano /etc/fail2ban/jail.local
# /etc/fail2ban/jail.local — configuración recomendada [DEFAULT] bantime = 1h # banear por 1 hora findtime = 10m # ventana de detección: 10 minutos maxretry = 5 # 5 intentos fallidos → ban ignoreip = 127.0.0.1/8 192.168.1.0/24 # nunca banear localhost ni LAN # Activar protección para SSH [sshd] enabled = true port = ssh logpath = %(sshd_log)s maxretry = 3 # más estricto para SSH bantime = 24h # 24 horas de ban # Protección para nginx (ataques a la web) [nginx-http-auth] enabled = true [nginx-botsearch] enabled = true maxretry = 2
FAIL2BAN
fail2ban — monitorización y gestión de bans
# Ver el estado de todos los jails activos $ sudo fail2ban-client status Status |- Number of jail: 2 `- Jail list: nginx-botsearch, sshd # Ver IPs baneadas por el jail SSH $ sudo fail2ban-client status sshd Status for the jail: sshd |- Filter | |- Currently failed: 3 | `- Total failed: 1247 `- Actions |- Currently banned: 12 `- Banned IP list: 185.234.218.47 103.99.0.122 ... # Desbanear una IP específica (si baneaste la tuya accidentalmente) $ sudo fail2ban-client set sshd unbanip 192.168.1.50 # Ver el log de fail2ban $ sudo tail -f /var/log/fail2ban.log 2025-01-15 03:45:14 INFO [sshd] Ban 185.234.218.47 # Recargar configuración después de cambios $ sudo systemctl restart fail2ban

Auditoría del sistema — ¿qué ha pasado aquí?
Los logs de seguridad más importantes y cómo analizarlos
logs de seguridad — análisis rápido
## AUTH.LOG — el log de seguridad más importante $ sudo tail -50 /var/log/auth.log # Intentos de login fallidos $ sudo grep "Failed password" /var/log/auth.log | wc -l 1247 # ¡1247 intentos! fail2ban los está bloqueando # Logins exitosos — verificar que son todos legítimos $ sudo grep "Accepted" /var/log/auth.log # Uso de sudo — auditar quién hizo qué como root $ sudo grep "sudo:" /var/log/auth.log | grep -v "pam_\|session" | tail -20 # Cuentas creadas/modificadas $ sudo grep "useradd\|usermod\|groupadd" /var/log/auth.log ## LAST — historial de logins $ last | head -20 # últimos logins exitosos $ lastb | head -20 # últimos logins fallidos $ lastlog # último login de cada usuario ## WHO — quién está conectado AHORA $ who $ w # más detallado — qué comando ejecuta cada usuario ## LYNIS — auditoría completa del sistema $ sudo apt install lynis $ sudo lynis audit system # análisis de seguridad completo # Genera un informe con sugerencias de mejora de seguridad # Hardening index: 0-100 (cuánto de seguro está el sistema)
rkhunter
Rootkit Hunter — busca rootkits, backdoors y archivos sospechosos en el sistema.
sudo apt install rkhunter sudo rkhunter --update sudo rkhunter --checkall
chkrootkit
Alternativa a rkhunter para detección de rootkits. Más simple y rápido.
sudo apt install chkrootkit sudo chkrootkit
auditd
El demonio de auditoría del kernel. Registra accesos a archivos, llamadas al sistema y cambios de privilegios.
sudo apt install auditd sudo auditctl -w /etc/passwd -p wa sudo ausearch -f /etc/passwd
debsums
Verifica la integridad de los archivos de paquetes instalados comparando con sus checksums originales.
sudo apt install debsums sudo debsums -c # solo archivos modificados

Sandboxing — aislar lo que no confías
AppArmor, Firejail, namespaces y cómo Linux aísla procesos

El sandboxing aisla un proceso para que, si es comprometido, el daño se contenga. En lugar de confiar en que el software es perfecto, asumes que puede ser vulnerable y limitas lo que puede hacer incluso si lo explotan.

AppArmor y Firejail — sandboxing práctico
## AppArmor — control de acceso obligatorio (MAC) # Ubuntu lo incluye por defecto $ sudo apt install apparmor-utils # Ver el estado de AppArmor $ sudo aa-status apparmor module is loaded. 34 profiles are loaded. 34 profiles are in enforce mode. /usr/bin/evince /usr/sbin/nginx # Ver qué perfil tiene un proceso $ sudo aa-status | grep nginx # nginx tiene un perfil que limita qué archivos puede leer/escribir ## Firejail — sandbox para apps de escritorio $ sudo apt install firejail # Ejecutar Firefox en sandbox (sin acceso a tu home completo) $ firejail firefox $ firejail --private firefox # home temporal y vacío $ firejail --net=none firefox # sin acceso a la red # Ejecutar un script desconocido de forma segura $ firejail --private --net=none bash script-sospechoso.sh ## seccomp — filtrar llamadas al sistema (nivel kernel) # Docker lo usa automáticamente para sus contenedores # systemd lo soporta en los unit files: # SystemCallFilter=@system-service (en el [Service] del unit file) ## Namespaces — el corazón del aislamiento en contenedores # Crear un proceso con su propio espacio de PIDs $ unshare --fork --pid --mount-proc bash $ ps aux # ¡solo ves los procesos de este namespace! PID USER COMMAND 1 hugo bash 2 hugo ps aux

📌 Docker es sandboxing de alto nivel

Los contenedores Docker usan exactamente estas tecnologías del kernel: namespaces para aislar PIDs, red, usuarios y sistema de archivos; cgroups para limitar CPU y RAM; y seccomp para filtrar syscalls. Cuando ejecutas docker run, el kernel crea un namespace completamente aislado del sistema host. Por eso Docker es tan popular en producción — combina aislamiento de seguridad con portabilidad.

MecanismoNivelUso típico

✏️ Ejercicio del Nivel 21 Seguridad

Audita y refuerza la seguridad de tu sistema:

  1. Actualizaciones: ejecuta sudo apt update && sudo apt list --upgradable 2>/dev/null | wc -l. ¿Cuántos paquetes tienen actualización disponible?
  2. Usuarios sudo: ejecuta grep -E '^sudo' /etc/group. ¿Quién tiene acceso sudo? ¿Hay usuarios inesperados?
  3. Intentos SSH: ejecuta sudo grep "Failed password" /var/log/auth.log 2>/dev/null | wc -l. ¿Cuántos intentos fallidos hay?
  4. UFW: instala y activa UFW: sudo apt install ufw && sudo ufw allow ssh && sudo ufw enable. Luego sudo ufw status.
  5. fail2ban: instala fail2ban y verifica que está activo: sudo apt install fail2ban && sudo fail2ban-client status.
  6. Logins: ejecuta last | head -10 y lastlog | grep -v "Never". ¿Ves solo tus propios logins?
  7. AppArmor: ejecuta sudo aa-status | head -10. ¿Cuántos perfiles están en enforce mode?

Auditoría con Lynis: sudo apt install lynis && sudo lynis audit system 2>&1 | tail -30. ¿Cuál es tu Hardening Index? ¿Qué sugerencias da?

🟥 Resumen del Nivel 21

  • Principios: mínimo privilegio, defensa en profundidad, reducir superficie de ataque y mantener el sistema actualizado.
  • unattended-upgrades — instala parches de seguridad automáticamente. La medida de mayor impacto con menor esfuerzo.
  • sudo seguro: limitar comandos en /etc/sudoers con visudo, revisar /var/log/auth.log, revocar acceso cuando no es necesario.
  • SSH seguro: PermitRootLogin no, PasswordAuthentication no (solo claves), AllowUsers, cambiar puerto. Validar con sshd -t antes de reiniciar.
  • UFW — firewall sencillo. Política por defecto: deny incoming. Abrir solo los puertos necesarios. ufw limit ssh para protección básica.
  • fail2ban — banea automáticamente IPs con demasiados intentos fallidos. Esencial en cualquier servidor público.
  • Auditoría: auth.log, last, lastb, who. Lynis para análisis completo. rkhunter para detectar rootkits.
  • Sandboxing: AppArmor (perfiles de acceso por proceso), Firejail (sandbox de escritorio), namespaces + cgroups (base de Docker).
