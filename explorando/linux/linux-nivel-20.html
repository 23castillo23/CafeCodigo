Conceptos clave de redes
IP, máscara, gateway, DNS y puertos — la base que necesitas conocer

Antes de los comandos, hay cuatro conceptos que lo explican todo en redes. Entenderlos hace que diagnosticar problemas de red sea intuitivo en lugar de mágico.

# El modelo de comunicación en red Tu equipo (192.168.1.42) │ ├── IP → tu dirección única en la red (como tu número de casa) ├── Máscara → define el tamaño de tu red (192.168.1.0/24 = 254 vecinos) ├── Gateway → la puerta de salida a internet (tu router: 192.168.1.1) └── DNS → el traductor nombre→IP (8.8.8.8 = Google DNS) # Cuando abres github.com: 1. Tu equipo pregunta al DNS: "¿qué IP es github.com?" 2. DNS responde: 140.82.114.4 3. Tu equipo envía paquetes a 140.82.114.4 vía el gateway 4. El servidor responde, tu navegador renderiza la página # Puertos — el número de apartamento dentro de una IP 192.168.1.42:80 → servidor web HTTP 192.168.1.42:443 → servidor web HTTPS 192.168.1.42:22 → servidor SSH 192.168.1.42:3000 → tu app Node.js en desarrollo
ConceptoQué esEjemplo
IP privadaDirección dentro de tu red local. No visible desde internet.192.168.1.42, 10.0.0.5
IP públicaDirección visible desde internet. La tiene el router, no tu equipo.189.247.134.82
LocalhostTu propio equipo. Siempre 127.0.0.1 o la dirección ::1 en IPv6.127.0.0.1, localhost
CIDR /24Notación de máscara. /24 = 255.255.255.0 = 254 hosts en la red.192.168.1.0/24

Interfaces de red — las tarjetas de red como archivos
ip link, NetworkManager y la gestión de interfaces en Linux

En Linux, cada tarjeta de red (física o virtual) es una interfaz de red con un nombre. Las interfaces modernas usan nombres predecibles basados en su tipo y posición hardware.

ver y gestionar interfaces de red
# ip link — ver todas las interfaces $ ip link show 1: lo: <LOOPBACK,UP> mtu 65536 state UNKNOWN link/loopback 00:00:00:00:00:00 2: enp3s0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP link/ether a0:b1:c2:d3:e4:f5 3: wlp2s0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP link/ether b0:c1:d2:e3:f4:05 # Nombres de interfaces explicados: # lo = loopback (127.0.0.1 - tu propio equipo) # enp3s0 = Ethernet, bus PCI 3, slot 0 # wlp2s0 = WiFi (wireless LAN), PCI 2, slot 0 # eth0 = nombre clásico (todavía en contenedores y VMs) # docker0 = interfaz del bridge de Docker # Activar / desactivar una interfaz $ sudo ip link set enp3s0 up $ sudo ip link set enp3s0 down # nmcli — controlar NetworkManager desde la terminal $ nmcli device status DEVICE TYPE STATE CONNECTION enp3s0 ethernet connected Ethernet wlp2s0 wifi connected MiRedWiFi # Conectarse a una WiFi con nmcli $ nmcli device wifi list # ver redes disponibles $ nmcli device wifi connect "MiRed" password "clave123" # Ver MAC address de una interfaz $ ip link show wlp2s0 | grep link/ether link/ether b0:c1:d2:e3:f4:05 brd ff:ff:ff:ff:ff:ff

Direcciones IP y tabla de rutas
ip addr, ip route — el comando ip reemplaza a ifconfig y route

El comando ip (del paquete iproute2) es la herramienta moderna para gestionar IPs y rutas en Linux. Reemplaza a los clásicos ifconfig y route que están obsoletos en distros modernas.

ip addr e ip route — IPs y tabla de rutas
# Ver todas las IPs asignadas $ ip addr show 2: enp3s0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 inet 192.168.1.42/24 brd 192.168.1.255 scope global dynamic enp3s0 3: wlp2s0: ... inet 192.168.1.55/24 brd 192.168.1.255 scope global dynamic wlp2s0 # Ver solo la IP de una interfaz específica $ ip addr show enp3s0 $ ip -4 addr show wlp2s0 # solo IPv4 # Asignar IP estática temporal (se pierde al reiniciar) $ sudo ip addr add 192.168.1.100/24 dev enp3s0 $ sudo ip addr del 192.168.1.100/24 dev enp3s0 # Ver la tabla de rutas $ ip route show default via 192.168.1.1 dev enp3s0 proto dhcp ← el gateway 192.168.1.0/24 dev enp3s0 proto kernel ← red local directa 172.17.0.0/16 dev docker0 proto kernel ← red de Docker # Ver el gateway por defecto $ ip route show default default via 192.168.1.1 dev enp3s0 # Ver tu IP pública (la que ve internet) $ curl ifconfig.me 189.247.134.82 $ curl https://ipinfo.io/ip # ifconfig — el clásico (obsoleto pero todavía instalable) $ sudo apt install net-tools $ ifconfig

DNS — resolver nombres de dominio
dig, nslookup, host y cómo funciona la resolución de nombres

DNS (Domain Name System) traduce nombres de dominio (github.com) a direcciones IP (140.82.114.4). Sin DNS tendrías que memorizar IPs para cada sitio que visitas. Linux consulta los servidores DNS configurados en /etc/resolv.conf.

DNS — consultar y diagnosticar
# Ver el DNS configurado $ cat /etc/resolv.conf nameserver 127.0.0.53 ← systemd-resolved (proxy local) nameserver 8.8.8.8 ← Google DNS (si configuras manualmente) # resolvectl — ver configuración DNS de systemd-resolved $ resolvectl status | head -20 Current DNS Server: 192.168.1.1 DNS Servers: 8.8.8.8 8.8.4.4 # dig — la herramienta de diagnóstico DNS más potente $ dig github.com ;; ANSWER SECTION: github.com. 60 IN A 140.82.114.4 # Tipos de registros DNS $ dig github.com A # dirección IPv4 $ dig github.com AAAA # dirección IPv6 $ dig github.com MX # servidores de correo $ dig github.com NS # servidores de nombres $ dig github.com TXT # registros de texto (SPF, DKIM...) # Usar un DNS específico para la consulta $ dig @8.8.8.8 github.com $ dig @1.1.1.1 example.com # host — más simple que dig $ host github.com github.com has address 140.82.114.4 github.com mail is handled by alt1.aspmx.l.google.com # nslookup — clásico, interactivo $ nslookup github.com $ nslookup github.com 8.8.8.8 # consultar servidor específico # /etc/hosts — resolución local que tiene precedencia sobre DNS $ cat /etc/hosts 127.0.0.1 localhost 127.0.1.1 mi-equipo # Puedes añadir entradas aquí para desarrollo local: # 127.0.0.1 api.local mi-app.local

🟢 /etc/hosts para desarrollo local

Añadir entradas en /etc/hosts es la forma más rápida de crear dominios locales para desarrollo: 127.0.0.1 miapp.local hace que http://miapp.local apunte a tu servidor local sin configurar DNS. Tiene precedencia sobre cualquier servidor DNS externo. Editar con sudo nano /etc/hosts.

Diagnóstico de red — ping, traceroute y más
Los comandos para encontrar dónde falla la conectividad
diagnóstico completo de red
## ping — comprobar conectividad básica $ ping google.com # ping continuo (Ctrl+C para parar) $ ping -c 4 google.com # solo 4 paquetes $ ping -i 0.2 google.com # cada 0.2 segundos (más rápido) $ ping 192.168.1.1 # probar conectividad con el gateway PING google.com (142.250.80.46): 56 bytes 64 bytes from 142.250.80.46: icmp_seq=1 ttl=113 time=18.4 ms ## traceroute — ver la ruta que siguen los paquetes $ traceroute google.com 1 192.168.1.1 2.341 ms ← tu router 2 10.0.0.1 8.234 ms ← router del ISP 3 72.14.238.114 14.123 ms ← Google backbone 4 142.250.80.46 18.432 ms ← destino # * * * = el router no responde ICMP (firewall) pero los paquetes pasan ## mtr — traceroute + ping en tiempo real (el mejor) $ sudo apt install mtr $ mtr google.com # interactivo con estadísticas en vivo $ mtr --report google.com # genera un reporte y sale ## Flujo de diagnóstico paso a paso $ ping 127.0.0.1 # 1. ¿funciona el loopback? $ ping 192.168.1.1 # 2. ¿llego al gateway/router? $ ping 8.8.8.8 # 3. ¿llego a internet (por IP)? $ ping google.com # 4. ¿funciona el DNS? # Si falla el 3 pero no el 2 → problema en el router/ISP # Si falla el 4 pero no el 3 → problema de DNS

curl y wget — el navegador de la terminal
Descargar archivos, hacer peticiones HTTP y consumir APIs desde la línea de comandos

curl y wget son las herramientas para hacer peticiones HTTP desde la terminal. curl es más versátil (APIs, autenticación, headers), wget es más simple para descargar archivos.

curl — el navaja suiza de HTTP
## GET básico $ curl https://example.com # muestra el HTML $ curl -o pagina.html https://example.com # guarda en archivo $ curl -L https://t.co/abc # -L sigue redirecciones $ curl -s https://api.github.com/zen # -s silencioso (sin progreso) ## Ver headers HTTP de respuesta $ curl -I https://example.com # solo headers $ curl -v https://example.com # verbose — ver todo * Connected to example.com port 443 > GET / HTTP/2 < HTTP/2 200 < content-type: text/html ## POST con JSON — consumir una API REST $ curl -X POST https://api.ejemplo.com/users \ -H "Content-Type: application/json" \ -H "Authorization: Bearer TOKEN" \ -d '{"nombre": "Hugo", "email": "hugo@example.com"}' ## Descargar archivo con progreso $ curl -O -L https://nodejs.org/dist/v20.0.0/node-v20.0.0-linux-x64.tar.gz # -O = nombre del archivo igual que el original ## Medir el tiempo de respuesta de un servidor $ curl -o /dev/null -s -w "tiempo: %{time_total}s\n" https://example.com tiempo: 0.234s ## wget — más simple, mejor para descargas recursivas $ wget https://ejemplo.com/archivo.tar.gz # descargar archivo $ wget -c https://ejemplo.com/grande.iso # -c reanudar descarga $ wget -r -np https://docs.ejemplo.com/ # descargar sitio recursivo

🟢 curl para probar APIs desde la terminal

curl es la herramienta estándar para probar APIs REST sin necesidad de Postman ni navegador. El truco básico: curl -s https://api.github.com/repos/torvalds/linux | python3 -m json.tool — la opción -s quita el progreso y python3 -m json.tool formatea el JSON para que sea legible.

SSH — administración remota segura
Claves SSH, túneles, config y las mejores prácticas de seguridad

SSH (Secure Shell) permite controlar un servidor remoto como si fuera tu propia terminal, con tráfico completamente cifrado. Es la herramienta más importante para administración de servidores Linux.

SSH — uso básico y avanzado
## CONEXIÓN BÁSICA $ ssh usuario@192.168.1.100 # conectar por IP $ ssh hugo@servidor.ejemplo.com # conectar por dominio $ ssh -p 2222 hugo@servidor.com # puerto no estándar ## GENERAR CLAVE SSH (hacer UNA vez) $ ssh-keygen -t ed25519 -C "hugo@miemail.com" # Genera: ~/.ssh/id_ed25519 (privada) y ~/.ssh/id_ed25519.pub (pública) # ed25519 es más moderno y seguro que rsa ## COPIAR CLAVE PÚBLICA AL SERVIDOR (autenticación sin contraseña) $ ssh-copy-id hugo@servidor.com # Añade tu clave pública a ~/.ssh/authorized_keys del servidor # A partir de aquí no pide contraseña ## COPIAR ARCHIVOS CON SSH $ scp archivo.txt hugo@servidor.com:/home/hugo/ # subir $ scp hugo@servidor.com:/logs/app.log ./ # bajar $ rsync -avz ./proyecto/ hugo@servidor.com:/app/ # sincronizar directorio ## TÚNELES SSH — magia de la red # Tunnel local: acceder a un puerto remoto en local $ ssh -L 8080:localhost:80 hugo@servidor.com # Ahora localhost:8080 apunta al puerto 80 del servidor # Tunnel remoto: exponer un puerto local al servidor $ ssh -R 3000:localhost:3000 hugo@servidor.com # El servidor puede acceder a tu app local en su puerto 3000 ## EJECUTAR COMANDO SIN SHELL INTERACTIVA $ ssh hugo@servidor.com "df -h" $ ssh hugo@servidor.com "sudo systemctl restart nginx"
# ~/.ssh/config — atajos para servidores frecuentes Host prod HostName 189.247.134.82 User hugo IdentityFile ~/.ssh/id_ed25519 Port 22 Host staging HostName servidor-staging.ejemplo.com User deploy IdentityFile ~/.ssh/deploy_key Host *.ejemplo.com User hugo IdentityFile ~/.ssh/id_ed25519 ServerAliveInterval 60 # mantener la conexión activa
SSH CONFIG

Con este archivo puedes simplemente escribir ssh prod en lugar del comando completo — mucho más cómodo.

🔑 Clave pública/privada
La privada (id_ed25519) se queda en tu equipo. La pública (id_ed25519.pub) va al servidor. Nunca compartas la privada.
🛡️ authorized_keys
~/.ssh/authorized_keys en el servidor lista las claves públicas que pueden conectarse sin contraseña.
🔒 known_hosts
~/.ssh/known_hosts guarda la huella de los servidores conocidos para detectar ataques MITM.
⚙️ sshd_config
/etc/ssh/sshd_config configura el servidor SSH. Aquí se desactiva el login con contraseña y se permiten solo claves.

⚠️ Deshabilitar el login por contraseña en SSH

Una vez configuradas las claves SSH, desactiva el login por contraseña en /etc/ssh/sshd_config: PasswordAuthentication no. Esto hace que los ataques de fuerza bruta sean inútiles — sin clave privada no hay acceso. Recuerda reiniciar SSH: sudo systemctl restart sshd. Pero ANTES verifica que puedes conectarte con tu clave — si la bloqueas y no tienes clave, te quedas fuera.

Puertos y conexiones activas
ss, netstat y nmap — qué servicios escuchan y qué conexiones hay activas
ss y netstat — puertos y conexiones
# ss — el sucesor moderno de netstat $ ss -tlnp # TCP, Listen, Numeric, Processes State Recv-Q Send-Q Local Address:Port Peer Address:Port Process LISTEN 0 128 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=1234)) LISTEN 0 511 0.0.0.0:80 0.0.0.0:* users:(("nginx",pid=2345)) LISTEN 0 128 0.0.0.0:443 0.0.0.0:* users:(("nginx",pid=2345)) LISTEN 0 5 127.0.0.1:5432 0.0.0.0:* users:(("postgres",pid=3456)) # Flags de ss: # -t = TCP -u = UDP -l = listening -n = numeric -p = processes # Ver TODAS las conexiones activas $ ss -tnp # sin -l = todas, no solo las que escuchan # Ver conexiones a un puerto específico $ ss -tnp | grep :443 # netstat — el clásico (necesita net-tools) $ sudo apt install net-tools $ netstat -tlnp # equivalente a ss -tlnp # nmap — escáner de puertos (para descubrir servicios en la red) $ sudo apt install nmap $ nmap localhost # puertos abiertos en tu propia máquina $ nmap 192.168.1.1 # puertos abiertos en el router $ nmap -p 1-1000 192.168.1.42 # escanear puertos 1-1000 $ nmap -sV 192.168.1.100 # detectar versiones de servicios

Monitorizar el tráfico de red
nethogs, iftop, tcpdump y cómo ver qué datos circulan por la red
nethogs
Muestra el ancho de banda usado por cada proceso — el "top" de la red.
sudo apt install nethogs sudo nethogs sudo nethogs wlp2s0
iftop
Muestra el tráfico en tiempo real por conexión — las IPs que más tráfico generan.
sudo apt install iftop sudo iftop sudo iftop -i enp3s0
tcpdump
Captura paquetes de red en bruto. Esencial para diagnóstico avanzado.
sudo tcpdump -i enp3s0 sudo tcpdump -i any port 80 sudo tcpdump -i any host 8.8.8.8
vnstat
Estadísticas de uso de ancho de banda por día, semana y mes. Persistente.
sudo apt install vnstat vnstat -d # uso diario vnstat -m # uso mensual
ip -s link
Ver estadísticas de paquetes enviados/recibidos y errores por interfaz.
ip -s link show enp3s0 # RX/TX packets, bytes, errors
watch ss
Monitorizar conexiones activas en tiempo real actualizando cada segundo.
watch -n 1 'ss -tnp | grep ESTAB'
tcpdump — captura de paquetes básica
# Capturar todo el tráfico HTTP (sin cifrar) $ sudo tcpdump -i enp3s0 port 80 -A # -A = mostrar contenido como ASCII # Capturar paquetes DNS $ sudo tcpdump -i any port 53 # Guardar captura para análisis en Wireshark $ sudo tcpdump -i enp3s0 -w captura.pcap # Abrir el .pcap con Wireshark para análisis visual # Ver cuánto tráfico genera tu sistema por interfaz $ cat /proc/net/dev Inter-| Receive | Transmit face | bytes packets | bytes packets enp3s0: 123456789 45678 | 9876543 23456
✏️ Ejercicio del Nivel 20 Redes

Explora la red de tu sistema desde la terminal:

  1. Interfaces: ejecuta ip link show y ip addr show. ¿Cuántas interfaces tienes? ¿Cuál es tu IP local?
  2. Gateway y rutas: ejecuta ip route show. ¿Cuál es tu gateway? ¿Qué otras rutas hay (Docker, VPN…)?
  3. IP pública: ejecuta curl -s ifconfig.me. ¿Cuál es tu IP pública? ¿Coincide con lo que ves en whatismyip.com?
  4. DNS: ejecuta dig github.com +short y dig @1.1.1.1 github.com +short. ¿Obtienes la misma IP con ambos?
  5. Diagnóstico: ejecuta el flujo completo: ping -c 2 127.0.0.1 && ping -c 2 $(ip route show default | awk '{print $3}') && ping -c 2 8.8.8.8 && ping -c 2 google.com.
  6. Puertos: ejecuta ss -tlnp. ¿Qué servicios están escuchando? ¿Hay algo en el puerto 22 (SSH)?
  7. SSH: si tienes SSH instalado (sudo apt install openssh-server), conéctate a ti mismo: ssh localhost. ¿Funciona?

Reto curl: ejecuta curl -s https://api.github.com/repos/torvalds/linux | python3 -m json.tool | grep -E '"name"|"stars"'. ¿Cuántas estrellas tiene el repositorio del kernel de Linux?

🟥 Resumen del Nivel 20

  • Conceptos base: IP (dirección), máscara (tamaño de red), gateway (puerta de salida), DNS (nombre→IP), puerto (servicio en una IP).
  • ip link show — interfaces. ip addr show — IPs asignadas. ip route show — tabla de rutas y gateway.
  • nmcli — gestionar conexiones de NetworkManager desde la terminal. nmcli device wifi connect para WiFi.
  • dig dominio — consulta DNS detallada. host dominio — simple. /etc/hosts tiene precedencia sobre DNS.
  • Flujo de diagnóstico: ping loopback → ping gateway → ping 8.8.8.8 → ping google.com. El paso que falla indica dónde está el problema.
  • mtr — mejor que traceroute para diagnóstico de rutas. Muestra estadísticas en vivo por salto.
  • curl — peticiones HTTP, APIs REST, descargas. wget — descargas simples y sitios completos.
  • SSH con claves: ssh-keygen -t ed25519 → ssh-copy-id usuario@servidor → ya no necesitas contraseña.
  • ~/.ssh/config define atajos para servidores frecuentes. ssh -L para túneles locales.
  • ss -tlnp — qué servicios escuchan en qué puertos. nethogs — qué proceso usa más red.
