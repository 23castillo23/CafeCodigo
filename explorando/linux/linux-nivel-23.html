Scripts Bash — automatizar con código
Variables, condicionales, bucles, funciones y las mejores prácticas

Un script Bash es un archivo de texto con comandos de shell que se ejecutan en secuencia. Todo lo que haces a mano en la terminal puede convertirse en un script — y ejecutarse automáticamente, sin errores, en cualquier sistema Linux.

#!/usr/bin/env bash # La primera línea (shebang) indica qué intérprete usar # #!/usr/bin/env bash es más portable que #!/bin/bash ## MEJORES PRÁCTICAS — siempre al principio set -euo pipefail # -e = salir si cualquier comando falla # -u = error si usas variable no definida # -o pipefail = el pipe falla si falla cualquier comando en la cadena ## VARIABLES NOMBRE="Hugo" # sin espacios alrededor del = FECHA=$(date +%Y-%m-%d) # comando en variable ARCHIVO="/tmp/backup-${FECHA}.tar.gz" echo "Hola, ${NOMBRE}. Fecha: ${FECHA}" echo "Archivo: ${ARCHIVO}" ## ARGUMENTOS DE LA LÍNEA DE COMANDOS # $0 = nombre del script $1 = primer arg $# = número de args $@ = todos echo "Script: $0, args: $#, primero: ${1:-'(ninguno)'}" # ${1:-'(ninguno)'} → valor por defecto si $1 no existe ## CONDICIONALES EDAD=25 if [[ "${EDAD}" -ge 18 ]]; then echo "Mayor de edad" elif [[ "${EDAD}" -ge 13 ]]; then echo "Adolescente" else echo "Menor" fi # Comprobar si un archivo existe if [[ -f "/etc/passwd" ]]; then echo "El archivo existe" fi # -f archivo -d directorio -e existe -r legible -x ejecutable ## BUCLES for i in 1 2 3 4 5; do echo "Iteración ${i}" done for archivo in /etc/*.conf; do echo "Procesando: ${archivo}" done while LINEA=$(read -r linea); do echo "Leí: ${linea}" done < /etc/hosts ## FUNCIONES saludar() { local nombre="${1}" # local = variable solo dentro de la función echo "¡Hola, ${nombre}!" return 0 # 0 = éxito, distinto de 0 = error } saludar "Hugo" saludar "Linux"
BASH
#!/usr/bin/env bash # EJEMPLO REAL: script de backup comprimido con fecha set -euo pipefail ORIGEN="${1:-$HOME}" # argumento o home por defecto DESTINO="/tmp/backups" FECHA=$(date +%Y%m%d_%H%M%S) ARCHIVO="${DESTINO}/backup_${FECHA}.tar.gz" log() { echo "[$(date +%H:%M:%S)] $*"; } log "Iniciando backup de ${ORIGEN}" mkdir -p "${DESTINO}" if tar -czf "${ARCHIVO}" "${ORIGEN}" 2>/dev/null; then TAMAÑO=$(du -sh "${ARCHIVO}" | cut -f1) log "✓ Backup completado: ${ARCHIVO} (${TAMAÑO})" else log "✗ Error al crear backup" exit 1 fi # Borrar backups más viejos de 7 días find "${DESTINO}" -name "backup_*.tar.gz" -mtime +7 -delete log "Backups antiguos eliminados"

🟢 shellcheck — el linter de Bash

shellcheck analiza tus scripts y señala errores comunes, variables sin comillas, uso incorrecto de condicionales y decenas de problemas típicos. Es la herramienta más valiosa para aprender Bash bien: sudo apt install shellcheck && shellcheck mi-script.sh. También funciona online en shellcheck.net.

Automatizar tareas — cron y systemd timers
Programar la ejecución de scripts de forma periódica sin intervención manual
cron y systemd timers
## CRON — el clásico planificador de tareas $ crontab -e # editar el crontab del usuario actual $ crontab -l # listar tareas programadas $ sudo crontab -e # crontab de root # FORMATO: minuto hora día_mes mes día_semana comando # 0 2 * * * /scripts/backup.sh → cada día a las 02:00 # */5 * * * * /scripts/check.sh → cada 5 minutos # 0 9 * * 1 /scripts/semanal.sh → lunes a las 09:00 # 0 0 1 * * /scripts/mensual.sh → día 1 de cada mes # Ejemplo de crontab completo: # m h dom mon dow command 0 2 * * * /home/hugo/scripts/backup.sh >> /var/log/backup.log 2>&1 */10 * * * * /home/hugo/scripts/monitor.sh ## SYSTEMD TIMERS — la alternativa moderna a cron # Crear un .service y un .timer en ~/.config/systemd/user/ # backup.service [Unit] Description=Backup diario [Service] Type=oneshot ExecStart=/home/hugo/scripts/backup.sh # backup.timer [Unit] Description=Ejecutar backup cada día [Timer] OnCalendar=*-*-* 02:00:00 Persistent=true [Install] WantedBy=timers.target $ systemctl --user enable --now backup.timer $ systemctl --user list-timers # ver todos los timers activos

Git — control de versiones en Linux
Los comandos esenciales para versionar tus scripts y proyectos

Git es el sistema de control de versiones creado por Linus Torvalds (el mismo creador de Linux) para gestionar el código del kernel. Hoy es el estándar universal para cualquier proyecto de software.

Git — flujo de trabajo diario completo
## CONFIGURACIÓN INICIAL (una sola vez) $ git config --global user.name "Hugo" $ git config --global user.email "hugo@ejemplo.com" $ git config --global init.defaultBranch main $ git config --global core.editor nano ## CREAR UN REPOSITORIO $ mkdir mi-proyecto && cd mi-proyecto $ git init Initialized empty Git repository in /home/hugo/mi-proyecto/.git/ ## FLUJO BÁSICO: trabajar → stage → commit $ echo "# Mi proyecto" > README.md $ git status # ver qué hay sin trackear $ git add README.md # añadir al área de stage $ git add . # añadir TODOS los cambios $ git commit -m "Primer commit: añado README" [main (root-commit) a1b2c3d] Primer commit: añado README ## HISTORIAL Y DIFERENCIAS $ git log --oneline # historial compacto $ git log --oneline --graph # con árbol de ramas $ git diff # cambios sin hacer stage $ git diff --staged # cambios en stage $ git show a1b2c3d # ver un commit específico ## RAMAS $ git branch feature/login # crear rama $ git switch feature/login # cambiar a la rama $ git switch -c fix/bug-42 # crear y cambiar en un paso $ git switch main # volver a main $ git merge feature/login # fusionar rama en main $ git branch -d feature/login # eliminar rama ya fusionada ## TRABAJAR CON GITHUB/GITLAB $ git clone https://github.com/usuario/repo.git $ git remote add origin https://github.com/usuario/repo.git $ git push -u origin main # primera vez $ git push # siguientes veces $ git pull # bajar cambios del remoto $ git fetch # bajar sin fusionar (más seguro) ## DESHACER COSAS $ git restore archivo.txt # descartar cambios sin stage $ git restore --staged archivo # sacar del stage $ git revert HEAD # deshacer el último commit (safe) $ git stash # guardar cambios temporalmente $ git stash pop # recuperar lo guardado

Docker — contenedores en Linux
La forma moderna de empaquetar y ejecutar aplicaciones aisladas

Docker usa namespaces, cgroups y overlayFS del kernel Linux (exactamente lo que viste en N22) para crear entornos completamente aislados — los contenedores. Un contenedor lleva su propia aplicación, dependencias y configuración, y se ejecuta igual en cualquier sistema Linux.

📦 Analogía — Contenedores de barco

Antes de los contenedores de transporte, cada carga necesitaba manipulación especial. Un contenedor estándar se carga en cualquier barco, tren o camión sin importar qué hay dentro. Docker hace lo mismo con el software: empaquetas tu app en un contenedor que se ejecuta igual en tu portátil, en el servidor de staging y en producción — sin el "en mi máquina funciona".

Docker — comandos esenciales
## INSTALACIÓN $ curl -fsSL https://get.docker.com | sh $ sudo usermod -aG docker $USER # usar Docker sin sudo (reiniciar sesión) ## IMÁGENES — la plantilla del contenedor $ docker pull ubuntu:24.04 # descargar imagen $ docker pull nginx:alpine # nginx con Alpine Linux (muy pequeño) $ docker images # ver imágenes descargadas $ docker rmi nginx:alpine # eliminar imagen ## CONTENEDORES — ejecutar imágenes $ docker run ubuntu:24.04 echo "Hola desde contenedor" $ docker run -it ubuntu:24.04 bash # -it = interactivo con terminal $ docker run -d -p 8080:80 nginx # -d daemon, -p puerto_host:puerto_cont → Abre http://localhost:8080 — nginx corriendo en el contenedor ## GESTIONAR CONTENEDORES $ docker ps # contenedores en ejecución $ docker ps -a # todos (incluidos parados) $ docker stop nombre_o_id # parar $ docker rm nombre_o_id # eliminar $ docker logs nombre # ver logs del contenedor $ docker exec -it nombre bash # entrar a un contenedor en marcha ## VOLÚMENES — persistir datos fuera del contenedor $ docker run -d -v ./datos:/var/lib/mysql mysql:8 ## CONSTRUIR TU PROPIA IMAGEN $ docker build -t mi-app:1.0 . # construir desde Dockerfile
# Dockerfile — receta para construir tu imagen FROM node:20-alpine # imagen base WORKDIR /app # directorio de trabajo dentro del contenedor COPY package*.json ./ # copiar primero para cache de layers RUN npm ci --only=production COPY . . # copiar el resto del código EXPOSE 3000 # documentar qué puerto expone USER node # no correr como root CMD ["node", "server.js"] # comando al iniciar el contenedor

Máquinas virtuales con KVM/QEMU
Virtualización nativa en Linux — más aislamiento que contenedores

KVM (Kernel-based Virtual Machine) convierte el kernel de Linux en un hipervisor nativo. A diferencia de los contenedores (que comparten el kernel), las VMs tienen su propio kernel completo — máximo aislamiento. Es lo que usan los proveedores cloud como base de sus servidores.

KVM/QEMU y libvirt — virtualización en Linux
## Verificar soporte de virtualización hardware $ grep -c "vmx\|svm" /proc/cpuinfo 12 ← > 0 = virtualización hardware disponible ## Instalar KVM + QEMU + libvirt (el stack completo) $ sudo apt install qemu-kvm libvirt-daemon-system virt-manager $ sudo usermod -aG kvm,libvirt $USER ## virt-manager — interfaz gráfica para gestionar VMs $ virt-manager # abre la GUI — la forma más fácil ## virsh — gestión de VMs desde la terminal $ virsh list --all # listar todas las VMs $ virsh start ubuntu-vm # iniciar una VM $ virsh shutdown ubuntu-vm # apagar limpiamente $ virsh destroy ubuntu-vm # forzar apagado $ virsh snapshot-create-as ubuntu-vm snap1 # snapshot ## Crear VM rápida con virt-install $ virt-install \ --name ubuntu-test \ --ram 2048 \ --vcpus 2 \ --disk size=20 \ --cdrom ~/ubuntu-24.04.iso \ --os-variant ubuntu24.04 ## Multipass — VMs Ubuntu con un comando (más fácil) $ sudo snap install multipass $ multipass launch --name dev --cpus 2 --memory 2G $ multipass shell dev # entrar a la VM $ multipass list # ver VMs $ multipass delete dev && multipass purge

La mentalidad Linux y Unix
Los principios que hacen que todo lo aprendido tenga sentido profundo

Más allá de los comandos, Linux tiene una filosofía — una forma de pensar el software que lleva décadas demostrando su valor. Entenderla hace que uses Linux de forma radicalmente más efectiva.

🔩
Haz una cosa y hazla bien
ls lista archivos. grep filtra texto. sort ordena. Cada herramienta tiene un propósito preciso — y lo hace perfectamente. Combínalas con pipes para cosas complejas.
📝
Todo es texto, todo es archivo
La configuración es texto. Los logs son texto. Los dispositivos son archivos. Esta uniformidad significa que puedes usar las mismas herramientas para todo: grep, cat, awk, sed.
🔗
Componer es más poderoso que integrar
cat log.txt | grep ERROR | awk '{print $3}' | sort | uniq -c | sort -rn — cinco herramientas simples compuestas hacen algo que ninguna hace sola.
🤖
Automatiza lo repetitivo
Si haces algo más de dos veces, escribe un script. El tiempo invertido en automatizar se recupera rápido. Los scripts también son documentación — muestran exactamente qué se hace y cómo.
🔍
Lee el manual
man comando siempre está ahí. comando --help también. La documentación está integrada en el sistema — no hay que buscar en internet lo que ya tienes a mano.
🏗️
Los errores son informativos
Linux no falla en silencio — te dice qué salió mal y dónde. Aprende a leer los mensajes de error. Están diseñados para diagnosticar el problema, no para frustrarte.
🎮
Experimenta — tienes las herramientas
Tienes --help, man, strace, dmesg, los logs. Experimenta con confianza — casi todo es reversible, y cuando no, aprendes algo valioso.
🌐
Está construido sobre colaboración
Linux es open source — puedes leer el código de cualquier herramienta. Millones de personas colaboran. Las preguntas tienen respuesta en la comunidad. Contribuye cuando puedas.

✏️ Proyecto Final — Nivel 23 Todo junto

El proyecto que une todo lo aprendido en la guía:

  1. Script de diagnóstico del sistema — crea ~/scripts/diagnostico.sh que muestre: versión del kernel, uptime, CPU (modelo y núcleos), RAM disponible, espacio en disco, IP local, carga del sistema, y los 5 procesos que más CPU consumen. Todo formateado con colores usando tput o códigos ANSI.
  2. Git para el script — inicializa un repositorio Git en ~/scripts/. Haz el primer commit. Añade un .gitignore que ignore archivos *.log y *.tmp. Haz un segundo commit.
  3. Automatizar — añade el script a cron para que se ejecute cada hora y guarde el resultado en ~/logs/diagnostico-$(date +%Y%m%d).log.
  4. Docker — si tienes Docker instalado: ejecuta docker run -d -p 8080:80 nginx y visita http://localhost:8080. Luego docker logs para ver los accesos.
  5. Explorar /proc — dentro de tu script, añade una sección que lea /proc/meminfo directamente (sin usar free) y muestre MemTotal y MemAvailable en MB.

Reto final: haz que el script de diagnóstico envíe una alerta por correo (mail) o escriba a syslog (logger) si la carga del sistema supera el número de núcleos — el sistema está sobrecargado. Consulta man logger para ver cómo integrar con systemd journal.

🟥 Resumen del Nivel 23

  • Scripts Bash: #!/usr/bin/env bash + set -euo pipefail. Variables, condicionales [[ ]], bucles for/while, funciones con local. Usa shellcheck para validar.
  • Automatización: cron (crontab -e) para tareas periódicas. systemd timers como alternativa moderna con mejor integración con el sistema.
  • Git: init → add → commit es el ciclo básico. branch/switch/merge para ramas. push/pull para sincronizar con remotos. stash para guardar trabajo temporal.
  • Docker: imagen = plantilla, contenedor = instancia en ejecución. run -d -p para servicios. -v para persistir datos. Dockerfile para construir imágenes propias.
  • KVM/QEMU: virtualización nativa del kernel. Más aislamiento que Docker (kernel propio) pero más overhead. virt-manager para GUI, virsh para terminal.
  • Mentalidad Unix: una herramienta = un propósito, texto como interfaz universal, componer > integrar, automatizar lo repetitivo, los errores son informativos.
  • Caminos siguientes: DevOps/Cloud, ciberseguridad, programación de sistemas, redes avanzadas, embedded — todos construyen sobre esta base.
