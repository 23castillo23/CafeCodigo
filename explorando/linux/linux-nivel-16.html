¿Qué es un proceso?
La unidad básica de ejecución en Linux — todo lo que corre es un proceso

Un proceso es un programa en ejecución. No el archivo ejecutable en disco — sino ese archivo cargado en memoria, con su propio espacio de direcciones, sus descriptores de archivo, su CPU time y su estado. Cada proceso tiene un PID (Process ID) único asignado por el kernel.

🏃 Analogía — La receta vs el cocinero

Un programa en disco es como una receta — son instrucciones estáticas escritas en papel. Un proceso es el cocinero ejecutando esa receta ahora mismo: tiene ingredientes (datos en RAM), usa utensilios (archivos abiertos, sockets), ocupa espacio en la cocina (memoria), tarda un tiempo (CPU), y puede crear ayudantes (procesos hijos). La misma receta puede ejecutarse por varios cocineros a la vez — igual que el mismo programa puede tener múltiples procesos.

# Qué contiene cada proceso Proceso PID 1847 (firefox) ├── PID 1847 ← identificador único ├── PPID 901 ← PID del proceso padre (gnome-shell) ├── UID/GID 1000 ← quién lo ejecuta (hugo) ├── Estado S ← durmiendo (sleeping) ├── Espacio memoria ← código, datos, heap, stack (virtual) ├── File descriptors ← archivos abiertos (stdin=0, stdout=1, stderr=2, ...) ├── Variables de entorno ← HOME, PATH, DISPLAY... ├── Directorio actual ← /home/hugo ├── CPU time ← cuánto tiempo de CPU ha consumido └── Prioridad (nice) ← qué tan prioritario es frente a otros # Relación padre-hijo: todo proceso tiene un padre excepto PID 1 systemd (1) → gnome-shell (901) → firefox (1847) → tab (2103)
información básica de procesos
# Tu propio PID en la shell actual $ echo $$ 12847 # PID del proceso padre de la shell $ echo $PPID 12840 # Ver el árbol de procesos completo $ pstree -p | head -20 systemd(1)─┬─NetworkManager(624) ├─gnome-shell(901)─┬─firefox(1847)─┬─firefox(2103) │ │ └─firefox(2198) │ └─code(2341) └─bash(12840)───bash(12847)───pstree(12901) # Encontrar el PID de un proceso por nombre $ pidof firefox 1847 2103 2198 $ pgrep -l firefox 1847 firefox 2103 firefox
🔄
Estados de un proceso
En qué situación puede estar un proceso en cada momento

Un proceso no siempre está usando la CPU activamente. Pasa por diferentes estados a lo largo de su vida. Entender estos estados es clave para diagnosticar problemas de rendimiento.

R
Running
Ejecutándose en la CPU ahora mismo, o en la cola del scheduler listo para ejecutarse.
S
Sleeping
Durmiendo, esperando un evento (tecla, dato de red, temporizador). El estado más común.
D
Disk Sleep
Esperando I/O de disco — no se puede interrumpir. Señales ignoradas. Malo si dura mucho.
Z
Zombie
Ha terminado pero el padre no recogió su código de salida. Solo ocupa una entrada en la tabla de procesos.
T
Stopped
Detenido por señal (Ctrl+Z) o por el debugger. Puede reanudarse con fg o SIGCONT.

💡 Muchos procesos en D es señal de problema

Si ves muchos procesos en estado D (Disk Sleep) en top, suele indicar un problema de I/O: disco muy lento, NFS colgado, o disco fallando. Los procesos en D no responden a señales (ni a SIGKILL), lo que puede hacer que el sistema parezca congelado. La solución suele ser identificar el dispositivo de almacenamiento problemático.

ps — snapshot de los procesos actuales
El comando para ver qué procesos están corriendo en un momento dado

ps (Process Status) muestra una fotografía instantánea de los procesos activos. A diferencia de top, no se actualiza en tiempo real — es una instantánea del momento en que lo ejecutas.

ps — todas las combinaciones útiles
# ps aux — el comando más usado, muestra TODOS los procesos $ ps aux USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND root 1 0.0 0.1 169680 12288 ? Ss 09:00 0:03 /sbin/init hugo 1847 3.2 8.4 3856204 685892 ? Sl 09:45 1:23 /usr/lib/firefox/firefox hugo 12847 0.0 0.0 10352 5120 pts/0 Ss 10:30 0:00 bash # a = todos los usuarios, u = formato usuario, x = sin terminal # Las columnas más importantes: # %CPU = porcentaje de CPU usado # %MEM = porcentaje de RAM física usada # VSZ = memoria virtual total (puede ser mucho mayor que la real) # RSS = memoria física real usada (Resident Set Size) # STAT = estado: R=running S=sleeping D=disk T=stopped Z=zombie # Ver procesos de un usuario específico $ ps -u hugo # Los 5 procesos que más CPU consumen $ ps aux --sort=-%cpu | head -6 # Los 5 procesos que más RAM consumen $ ps aux --sort=-%mem | head -6 # Buscar un proceso específico $ ps aux | grep firefox hugo 1847 3.2 8.4 ... /usr/lib/firefox/firefox # Ver el árbol de procesos con ps $ ps auxf | head -25 # f = forest (árbol) # Formato personalizado — ver solo lo que necesitas $ ps -eo pid,ppid,user,stat,%cpu,%mem,comm --sort=-%cpu | head -10
📊
top y htop — monitorización en tiempo real
La diferencia entre una fotografía (ps) y una película (top/htop)

top es el monitor de procesos interactivo incluido en todos los sistemas Linux. htop es su versión moderna con colores, barras visuales y manejo con ratón. Si no lo tienes: sudo apt install htop.

top — uso básico e interacción
# Lanzar top $ top # Lo que muestra la cabecera: top - 10:45:12 up 1:23, 1 user, load average: 0.42, 0.51, 0.48 # uptime, usuarios conectados, carga media (1, 5, 15 minutos) Tasks: 287 total, 1 running, 286 sleeping, 0 stopped, 0 zombie %Cpu(s): 3.2 us, 1.1 sy, 0.0 ni, 94.8 id, 0.8 wa, 0.0 hi, 0.1 si # us=user sy=system id=idle wa=waiting(I/O) — el wa alto indica problema de disco MiB Mem: 15809.6 total, 8234.1 free, 5821.4 used, 1754.1 buff/cache MiB Swap: 2048.0 total, 2048.0 free, 0.0 used. 9231.2 avail Mem # Atajos de teclado dentro de top: # q → salir # k → matar proceso (te pide el PID) # r → cambiar prioridad (renice) # M → ordenar por uso de memoria # P → ordenar por uso de CPU (por defecto) # 1 → mostrar cada núcleo de CPU por separado # u → filtrar por usuario # H → mostrar hilos (threads) en lugar de procesos # Espacio → actualizar ahora mismo
htop — el top moderno (instalar: sudo apt install htop)
# Lanzar htop $ htop # Ventajas de htop sobre top: # - Barras de CPU, RAM y Swap a color y en tiempo real # - Navegación con flechas, clic de ratón # - F3 → buscar proceso por nombre # - F4 → filtrar por nombre # - F5 → vista de árbol (tree view) # - F6 → cambiar columna de ordenación # - F9 → enviar señal al proceso (menú visual) # - F10 → salir # htop con vista de árbol desde la línea de comandos $ htop -t # Otras herramientas de monitorización: $ btop # el más moderno y hermoso (apt install btop) $ glances # monitor completo del sistema (apt install glances) $ iotop # monitorización de I/O de disco por proceso $ nethogs # monitorización de red por proceso
📡
Señales — el sistema de mensajería entre procesos
Cómo el kernel y otros procesos comunican eventos a un proceso en ejecución

Una señal es una notificación asíncrona que el kernel (o un proceso) envía a otro proceso. El proceso puede capturar la señal y decidir qué hacer, o ignorarla — excepto SIGKILL y SIGSTOP, que no pueden ser ignoradas ni capturadas.

📟 Analogía — El buscapersonas del proceso

Las señales son como mensajes en un buscapersonas de los años 90. No interrumpen lo que estás haciendo de forma inmediata — el proceso las recibe cuando puede y decide cómo responder. Algunos mensajes son sugerencias corteses ("termina cuando puedas" — SIGTERM), otros son órdenes directas del jefe que no puedes ignorar ("para ahora mismo" — SIGKILL).

1
SIGHUP
Colgar (hangup). Históricamente: terminal cerrada. Hoy: recargar configuración sin reiniciar el proceso.
2
SIGINT
Interrupción. Lo que envía Ctrl+C. Termina el proceso amablemente. El proceso puede capturarla.
3
SIGQUIT
Quit. Como SIGINT pero genera un core dump. Lo envía Ctrl+\.
9
SIGKILL
Matar inmediatamente. El kernel lo ejecuta directamente. NO puede ser capturada ni ignorada. Último recurso.
15
SIGTERM
Terminar. La señal por defecto de kill. Pide amablemente que el proceso termine. El proceso puede capturarla para hacer limpieza.
17
SIGCHLD
Un proceso hijo terminó. El padre la recibe para poder recoger el estado de salida (wait).
18
SIGCONT
Continuar. Reanuda un proceso que fue detenido con SIGSTOP o SIGTSTP (Ctrl+Z).
19
SIGSTOP
Detener (no terminar). NO puede ser capturada. Pausa el proceso hasta recibir SIGCONT.
20
SIGTSTP
Terminal stop. Lo envía Ctrl+Z. Como SIGSTOP pero el proceso SÍ puede capturarla.
10
SIGUSR1/2
Señales definidas por el usuario. Cada aplicación decide qué significan. Nginx las usa para rotar logs.
ver todas las señales disponibles
# Ver todas las señales disponibles en el sistema $ kill -l 1) SIGHUP 2) SIGINT 3) SIGQUIT 4) SIGILL 5) SIGTRAP 6) SIGABRT 7) SIGBUS 8) SIGFPE 9) SIGKILL 10) SIGUSR1 11) SIGSEGV 12) SIGUSR2 13) SIGPIPE 14) SIGALRM 15) SIGTERM ... # Caso real: nginx recarga configuración con SIGHUP sin reiniciar $ sudo kill -HUP $(pidof nginx) # nginx captura SIGHUP y recarga nginx.conf en caliente
🔫
kill, killall y pkill — enviar señales
Las herramientas para terminar (o controlar) procesos desde la terminal
kill, killall y pkill
## kill — envía señal a un PID específico $ kill 1847 # SIGTERM (15) por defecto — terminar amablemente $ kill -15 1847 # SIGTERM explícito $ kill -9 1847 # SIGKILL — matar sin piedad (último recurso) $ kill -HUP 1847 # SIGHUP — recargar configuración $ kill -STOP 1847 # pausar el proceso $ kill -CONT 1847 # reanudar el proceso ## killall — envía señal a todos los procesos con ese nombre $ killall firefox # termina todos los procesos llamados "firefox" $ killall -9 firefox # mata todos sin contemplaciones $ killall -u hugo # termina todos los procesos del usuario hugo ## pkill — como killall pero con patrones y más opciones $ pkill firefox # igual que killall firefox $ pkill -u hugo # matar procesos del usuario hugo $ pkill -f "python script.py" # busca en el comando completo, no solo el nombre ## El orden correcto para matar un proceso que no responde: $ kill -15 PID # 1. pedir amablemente (esperar unos segundos) $ kill -9 PID # 2. si no responde, matar a la fuerza

⚠️ SIGKILL (-9) como último recurso

SIGKILL mata el proceso inmediatamente sin darle oportunidad de limpiar. Esto puede dejar archivos corruptos, bases de datos inconsistentes, archivos de lock sin eliminar o datos sin escribir al disco. Siempre intenta SIGTERM primero y espera unos segundos. Si el proceso ignora SIGTERM, entonces usa SIGKILL.

🎛️
Jobs — procesos en primer y segundo plano
Cómo mover procesos entre el frente y el fondo de la terminal

Cada terminal tiene un conjunto de jobs (trabajos): el proceso en primer plano (foreground) que recibe la entrada del teclado, y procesos en segundo plano (background) que corren sin ocupar la terminal.

comando
Ejecutar en primer plano — bloquea la terminal hasta que termina
comando &
Ejecutar en segundo plano — la terminal queda libre inmediatamente
Ctrl+Z
Suspender el proceso en primer plano (SIGTSTP) — queda pausado en background
fg
Traer el último job suspendido/background de vuelta al primer plano
bg
Reanudar el último job suspendido en segundo plano (sin bloqueante)
jobs
Listar todos los jobs de la sesión actual con su número y estado
jobs — control completo de procesos en la terminal
# Lanzar un proceso en segundo plano con & $ npm run dev & [1] 2847 # [1] = número de job, 2847 = PID # Lanzar otro proceso largo $ python3 servidor.py & [2] 2901 # Ver todos los jobs activos $ jobs [1] Running npm run dev & [2]- Running python3 servidor.py & # Traer el job [1] al frente $ fg 1 npm run dev # Suspenderlo con Ctrl+Z # ^Z [1]+ Stopped npm run dev # Reanudar en segundo plano $ bg 1 [1]+ npm run dev & # Matar un job por su número $ kill %1 # el % indica número de job, no PID $ kill %2 # Proceso que sobrevive al cerrar la terminal $ nohup python3 servidor.py & # ignora SIGHUP al cerrar terminal $ disown %1 # desasociar job de la terminal

🟢 tmux — la solución definitiva para sesiones persistentes

tmux es un multiplexor de terminal que mantiene sesiones activas aunque cierres la terminal o pierdas la conexión SSH. Puedes desconectarte de una sesión tmux y al volver todo sigue corriendo exactamente donde lo dejaste. Es la herramienta esencial para trabajo en servidores remotos: tmux new -s trabajo, trabaja, Ctrl+B D para desconectar, tmux attach -t trabajo para reconectar.

Nice y renice — prioridad de procesos
Controlar cuánta CPU recibe un proceso en relación con los demás

El scheduler del kernel asigna tiempo de CPU según la prioridad de cada proceso. La prioridad de usuario se controla con el valor nice — un número de -20 (máxima prioridad) a +19 (mínima prioridad). Los usuarios normales solo pueden bajar la prioridad de sus propios procesos (aumentar el nice). Root puede hacer cualquier cosa.

🍽️ Analogía — El buffet con orden de preferencia

El scheduler es el chef de un buffet con capacidad limitada. El valor nice es qué tan "amable" (nice) es el proceso con los demás — cuánto cede su turno. Un nice de -20 es el VIP que siempre come primero. Un nice de +19 es el comensal más educado que siempre deja pasar a todos y come cuando sobra. Los usuarios normales no pueden convertirse en VIP (no pueden bajar el nice) — pero sí pueden ser más amables.

nice y renice — gestionar prioridades
# Ver la prioridad de los procesos en ps $ ps -eo pid,ni,comm --sort=ni | head -10 PID NI COMMAND 1 0 systemd 1847 0 firefox 2341 0 code # Lanzar un proceso con baja prioridad (nice alto) $ nice -n 19 make -j$(nproc) # compilación en background sin molestar $ nice -n 10 rsync -a /datos/ /backup/ # backup que no roba CPU # Cambiar la prioridad de un proceso ya en ejecución $ renice -n 15 -p 1847 # bajar prioridad de firefox (PID 1847) $ sudo renice -n -5 -p 901 # subir prioridad (solo root) # Ver nice en htop: la columna NI # En top: la columna NI también muestra el nice value # Caso de uso real: compilar el kernel sin que el sistema se ponga lento $ nice -n 19 make -j$(nproc) 2>&1 | tee compilacion.log &
nice -n 19 cmd
Lanzar comando con la mínima prioridad. El sistema seguirá respondiendo bien mientras compila, hace backup o encode.
nice -n 19 ffmpeg -i video.mp4 out.mkv
renice
Cambiar la prioridad de un proceso ya en ejecución sin reiniciarlo.
renice -n 10 -p $(pidof code)
ionice
Como nice pero para I/O de disco. Útil para backups que no deben afectar la velocidad del disco.
ionice -c 3 rsync -a src/ dst/
taskset
Fijar un proceso a núcleos de CPU específicos (CPU affinity). Útil para benchmarks o tiempo real.
taskset -c 0,1 ./programa
✏️ Ejercicio del Nivel 16 Diagnóstico

Practica la gestión de procesos en tu sistema:

  1. Árbol de procesos: ejecuta pstree -p | head -30. ¿Puedes trazar el árbol desde systemd hasta tu terminal?
  2. ps: ejecuta ps aux --sort=-%mem | head -8. ¿Cuál es el proceso que más RAM consume? ¿Cuánto % usa?
  3. Estados: ejecuta ps aux | awk '{print $8}' | sort | uniq -c | sort -rn. ¿Cuántos procesos hay en cada estado (S, R, D, Z)?
  4. top: ejecuta top. Pulsa 1 para ver cada núcleo, M para ordenar por memoria, q para salir.
  5. Jobs: lanza sleep 100 &. Luego sleep 200 &. Ejecuta jobs — ¿ves los dos? Mata el primero con kill %1. Verifica con jobs de nuevo.
  6. Señales: lanza sleep 1000 (sin &, en primer plano). Pulsa Ctrl+Z. ¿Qué estado tiene ahora? Escribe bg para pasarlo a background. Ahora kill %1.
  7. nice: ejecuta nice -n 19 find / -name "*.log" 2>/dev/null > /tmp/logs.txt &. Mientras corre, el sistema sigue respondiendo normal. ¿Por qué?

Reto de diagnóstico: Ejecuta ps aux | grep -v grep | grep Z — ¿tienes procesos zombie? Si sí, ¿cuál es su PPID y por qué el padre no los recolectó?

🟥 Resumen del Nivel 16

  • Un proceso es un programa en ejecución con PID único, espacio de memoria propio, estado y relación padre-hijo.
  • Estados: R (running), S (sleeping, normal), D (esperando I/O, preocupante si dura), Z (zombie), T (stopped).
  • ps aux — snapshot de todos los procesos. --sort=-%cpu y --sort=-%mem para ordenar.
  • top y htop — monitorización en tiempo real. htop es más amigable. btop es el más moderno.
  • Señales: SIGTERM (15) termina amablemente, SIGKILL (9) mata inmediatamente sin posibilidad de captura, SIGHUP (1) recarga configuración.
  • kill PID, killall nombre, pkill patrón — enviar señales. Siempre SIGTERM primero, SIGKILL solo como último recurso.
  • Jobs: comando & en background, Ctrl+Z suspender, fg traer al frente, bg reanudar en background, jobs listar.
  • nohup comando & — proceso que sobrevive al cerrar la terminal. tmux para sesiones persistentes.
  • Nice: -20 (máxima prioridad) a +19 (mínima). nice -n 19 cmd para tareas pesadas que no deben molestar.
