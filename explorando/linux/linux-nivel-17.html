🚀 Nivel 17 — Arranque y Servicios
🗺️
La secuencia completa de arranque
Del botón de encendido al escritorio listo — 6 etapas bien diferenciadas

Cada vez que enciendes tu equipo Linux ocurre una secuencia precisa y ordenada de 6 etapas. Entenderla te permite diagnosticar dónde falla el sistema cuando no arranca y configurar el comportamiento del inicio.

🏗️ Analogía — Abrir una empresa cada mañana

El arranque de Linux es como abrir una empresa cada mañana: el vigilante (UEFI) verifica que el edificio está en buen estado y abre la puerta principal. El portero (GRUB) pregunta a qué planta vas (qué SO arrancar). El ascensor (kernel + initrd) te sube a la planta correcta con el equipamiento mínimo. El director de operaciones (systemd) abre todas las oficinas en el orden correcto. Los empleados (servicios) van llegando y ocupando sus puestos. Finalmente el recepcionista (display manager) recibe a los usuarios.

1
🔩
UEFI / BIOS — firmware del hardware
La CPU arranca y ejecuta el firmware de la placa base. Hace el POST (Power-On Self Test), inicializa RAM, detecta dispositivos y busca el bootloader en el disco. UEFI es el moderno, BIOS el clásico.
2
🥾
GRUB — el gestor de arranque
UEFI carga GRUB desde la partición EFI. GRUB muestra el menú (si hay varios SO), carga el kernel de Linux y el initrd en RAM, y transfiere el control al kernel.
3
🐧
Kernel Linux — el núcleo toma el control
El kernel se descomprime, detecta el hardware, carga los drivers esenciales, monta el initrd (un sistema de archivos temporal en RAM) y arranca el proceso PID 1.
4
⚙️
systemd — PID 1, el director de todo
systemd es el primer proceso de usuario. Lee sus units, calcula el orden y las dependencias entre servicios, y los arranca en paralelo donde puede. Monta el sistema de archivos raíz real.
5
🛠️
Servicios — el sistema cobra vida
systemd arranca los servicios en el orden correcto: red (NetworkManager), audio (PipeWire), Bluetooth, impresoras, base de datos… Cada servicio tiene sus dependencias declaradas.
6
🖥️
Display Manager — la pantalla de login
GDM (GNOME), SDDM (KDE) o LightDM muestra la pantalla de inicio de sesión. Al autenticarte, lanza la sesión del escritorio (GNOME Shell, Plasma, etc.).
🔩
UEFI y BIOS — el firmware de la placa base
Lo primero que ejecuta la CPU — antes de cualquier sistema operativo

El firmware es software grabado en un chip de la placa base que se ejecuta antes que cualquier cosa en el disco. Tiene dos generaciones: el clásico BIOS (desde los años 80) y el moderno UEFI (desde 2005), que es el estándar actual.

Partición de bootMBR en los primeros 512 bytesPartición ESP (EFI System Partition) FAT32

# Verificar si el sistema arrancó en modo UEFI o BIOS legacy $ ls /sys/firmware/efi efivars/ fw_platform_size runtime runtime-map systab vars # Si existe /sys/firmware/efi → UEFI. Si no existe → BIOS legacy # Ver las entradas de arranque UEFI $ sudo efibootmgr BootCurrent: 0001 BootOrder: 0001,0000,0002 Boot0000* Windows Boot Manager Boot0001* ubuntu Boot0002* UEFI: USB SanDisk # Ver la partición EFI montada $ ls /boot/efi/EFI/ BOOT/ ubuntu/ Microsoft/ # Ver los archivos del bootloader $ ls /boot/efi/EFI/ubuntu/ grubx64.efi shimx64.efi mmx64.efi BOOTX64.CSV

📌 Secure Boot y Linux

Secure Boot es una función de UEFI que verifica que el bootloader esté firmado digitalmente antes de ejecutarlo. Ubuntu y Fedora incluyen un shim (shimx64.efi) firmado por Microsoft que actúa de intermediario, permitiendo arrancar con Secure Boot activado. Si tienes problemas instalando Linux, desactivar Secure Boot en la UEFI suele resolver el conflicto — aunque es más seguro dejarlo activado si el sistema lo soporta.

🥾
GRUB — el gestor de arranque
El menú que aparece antes de que Linux cargue — y cómo configurarlo

GRUB (GRand Unified Bootloader) es el gestor de arranque más usado en Linux. Es lo que muestra el menú con las opciones de SO, carga el kernel y le pasa parámetros de configuración. GRUB 2 es la versión actual.

GRUB — configuración y gestión
# El archivo de configuración principal de GRUB $ cat /etc/default/grub GRUB_DEFAULT=0 GRUB_TIMEOUT=5 GRUB_TIMEOUT_STYLE=hidden GRUB_CMDLINE_LINUX_DEFAULT="quiet splash" GRUB_CMDLINE_LINUX="" # Cambiar timeout del menú GRUB (en segundos) # Editar /etc/default/grub: # GRUB_TIMEOUT=10 → espera 10 segundos # GRUB_TIMEOUT_STYLE=menu → mostrar siempre el menú # Aplicar cambios — SIEMPRE ejecutar después de editar /etc/default/grub $ sudo update-grub Generating grub configuration file ... Found linux image: /boot/vmlinuz-6.8.0-45-generic Found initrd image: /boot/initrd.img-6.8.0-45-generic Found Windows Boot Manager on /dev/nvme0n1p1 done # Ver los kernels disponibles para arrancar $ ls /boot/vmlinuz* /boot/vmlinuz-6.8.0-45-generic /boot/vmlinuz-6.8.0-40-generic # Ver los parámetros con los que arrancó el kernel actual $ cat /proc/cmdline BOOT_IMAGE=/vmlinuz-6.8.0-45-generic root=/dev/nvme0n1p2 ro quiet splash

🟢 Modo recovery desde GRUB

Si Linux no arranca, mantén pulsado Shift (BIOS) o Escape (UEFI) durante el inicio para forzar la aparición del menú GRUB. Desde ahí puedes seleccionar Advanced options for Ubuntu → recovery mode. El modo recovery arranca el sistema con el mínimo indispensable y te da acceso a herramientas de reparación: comprobar el sistema de archivos, reparar el grub, resetear contraseñas o acceder a una shell de root.

🐧
Kernel + initrd — el arranque real de Linux
Cómo el kernel se descomprime, detecta hardware y monta el sistema de archivos

GRUB carga dos archivos en RAM: el kernel (vmlinuz) comprimido y el initrd (Initial RAM Disk), un sistema de archivos temporal mínimo. Juntos permiten al kernel arrancar sin acceder aún al disco real.

# Los archivos de arranque en /boot/ /boot/ ├── vmlinuz-6.8.0-45-generic ← el kernel comprimido (virt-mem linux zip) ├── initrd.img-6.8.0-45-generic ← initramfs — sistema de archivos temporal ├── config-6.8.0-45-generic ← opciones con las que se compiló el kernel ├── System.map-6.8.0-45-generic ← tabla de símbolos del kernel (debugging) └── grub/ ← configuración y archivos de GRUB # Secuencia detallada kernel + initrd: 1. GRUB carga vmlinuz + initrd en RAM 2. Kernel se descomprime y toma control de la CPU 3. Kernel inicializa subsistemas: memoria, scheduler, drivers básicos 4. Kernel monta el initrd como sistema de archivos temporal (/) 5. initrd contiene los drivers para acceder al disco real 6. Con esos drivers, kernel monta el sistema de archivos raíz real (/dev/nvme0n1p2) 7. Kernel lanza /sbin/init (que es systemd) — PID 1 8. initrd se desmonta — el sistema raíz real toma el control

💡 ¿Por qué existe el initrd?

El kernel en disco no puede incluir drivers para todos los sistemas de archivos y controladoras de disco del mundo — sería enorme. El initrd resuelve este huevo-gallina: contiene los drivers mínimos para que el kernel pueda acceder al disco, donde están los drivers completos. Es un sistema de archivos bootstrap — existe solo para arrancar el sistema real.

información del kernel en ejecución
# Ver la versión del kernel en ejecución $ uname -r 6.8.0-45-generic # Información completa del kernel $ uname -a Linux ubuntu 6.8.0-45-generic #45~22.04.1-Ubuntu SMP PREEMPT_DYNAMIC x86_64 GNU/Linux # Ver los parámetros de arranque del kernel $ cat /proc/cmdline BOOT_IMAGE=/boot/vmlinuz-6.8.0-45-generic root=UUID=a1b2c3d4 ro quiet splash # Ver los módulos del kernel cargados $ lsmod | wc -l 89 $ lsmod | grep nvidia # ver si el driver NVIDIA está cargado # Cargar y descargar módulos del kernel manualmente $ sudo modprobe bluetooth # cargar módulo bluetooth $ sudo rmmod bluetooth # descargar módulo # Ver los mensajes del kernel durante el arranque $ dmesg | head -50 $ dmesg | grep -i error $ dmesg --follow # modo live — muestra mensajes en tiempo real
⚙️
systemd — PID 1, el director de operaciones
El sistema de init moderno que gestiona el arranque y todos los servicios

systemd es el sistema de init más usado en Linux moderno (Ubuntu, Fedora, Debian, Arch…). Es el PID 1 — el primer proceso de usuario que lanza el kernel. Se encarga de arrancar todos los servicios, gestionar el sistema de archivos, los sockets, los timers y los logs.

🎼 Analogía — El director de orquesta

systemd es el director de orquesta. Tiene la partitura completa (sus archivos de configuración llamados units). Sabe qué músico (servicio) debe tocar antes que otro (dependencias). Puede hacer que varios toquen al mismo tiempo si no dependen entre sí (arranque paralelo). Si un músico falla, decide si parar la obra o continuar. Y si alguien abandona el escenario, puede reemplazarlo automáticamente (restart on failure).

# systemd targets — como los "runlevels" del viejo init poweroff.target → apagar el sistema rescue.target → modo rescate (shell de root, mínimo de servicios) multi-user.target → sistema multiusuario sin escritorio (servidores) graphical.target → sistema completo con escritorio (desktops) ← el habitual reboot.target → reiniciar el sistema emergency.target → emergencia — solo la shell root, sin nada más # Ver el target activo $ systemctl get-default graphical.target # Cambiar el target por defecto (útil en servidores) $ sudo systemctl set-default multi-user.target
📄
Unit files — los archivos de configuración de systemd
Cómo se define un servicio para que systemd lo gestione

Todo en systemd se describe mediante unit files — archivos de texto con formato INI que definen servicios, sockets, timers, dispositivos y más. Los encontrarás en /lib/systemd/system/ (del sistema) y /etc/systemd/system/ (personalizados).

[Unit]
Descripción del servicio, dependencias (After=, Requires=, Wants=) y condiciones de arranque.
[Service]
Cómo ejecutar el servicio: tipo (simple, forking, oneshot…), usuario, comando a ejecutar, política de reinicio.
[Install]
En qué target debe activarse este servicio. WantedBy=multi-user.target es lo más común.
# /etc/systemd/system/mi-app.service # Ejemplo de unit file para una aplicación web [Unit] Description=Mi aplicación web Node.js After=network.target # arrancar después de que la red esté lista Wants=network-online.target [Service] Type=simple User=hugo # ejecutar como usuario hugo, no como root WorkingDirectory=/home/hugo/mi-app ExecStart=/usr/bin/node server.js Restart=always # reiniciar si el proceso cae RestartSec=5 # esperar 5s antes de reintentar StandardOutput=journal # logs → journald StandardError=journal Environment=NODE_ENV=production PORT=3000 [Install] WantedBy=multi-user.target # activar en arranque normal
SYSTEMD UNIT
activar un unit file personalizado
# 1. Crear el archivo de unit $ sudo nano /etc/systemd/system/mi-app.service # 2. Recargar systemd para que lea el nuevo archivo $ sudo systemctl daemon-reload # 3. Habilitar el servicio (lo añade al arranque automático) $ sudo systemctl enable mi-app.service # 4. Iniciarlo ahora mismo $ sudo systemctl start mi-app.service # 5. Verificar que corre correctamente $ systemctl status mi-app.service
🛠️
systemctl — gestionar servicios en el día a día
Los comandos que más usarás para controlar servicios del sistema
systemctl — todos los comandos esenciales
## ESTADO E INFORMACIÓN $ systemctl status nginx # estado detallado + últimas líneas de log $ systemctl is-active nginx # "active" o "inactive" $ systemctl is-enabled nginx # "enabled" o "disabled" $ systemctl list-units --type=service --state=running # servicios activos $ systemctl list-unit-files # todos los unit files y su estado ## CONTROL BÁSICO $ sudo systemctl start nginx # iniciar $ sudo systemctl stop nginx # detener $ sudo systemctl restart nginx # reiniciar (para + inicia) $ sudo systemctl reload nginx # recargar config sin reiniciar $ sudo systemctl reload-or-restart nginx # recarga si puede, sino reinicia ## ARRANQUE AUTOMÁTICO $ sudo systemctl enable nginx # activar en el arranque del sistema $ sudo systemctl disable nginx # desactivar del arranque $ sudo systemctl enable --now nginx # habilitar E iniciar ahora (atajo) $ sudo systemctl mask nginx # deshabilitar completamente (no puede iniciar) $ sudo systemctl unmask nginx # deshacer mask ## SISTEMA $ sudo systemctl reboot # reiniciar el sistema $ sudo systemctl poweroff # apagar $ sudo systemctl suspend # suspender $ sudo systemctl hibernate # hibernar
systemctl status
Muestra estado, PID, memoria usada, últimas líneas del log y si está habilitado para el arranque.
systemctl status ssh systemctl status nginx.service
enable vs start
enable = arranque automático en el boot (persistente). start = iniciar ahora mismo (solo esta vez).
sudo systemctl enable --now ssh # equivale a: enable + start
daemon-reload
Obligatorio después de crear o modificar un unit file. Recarga systemd sin reiniciar nada.
sudo systemctl daemon-reload
list-dependencies
Ver el árbol de dependencias de un servicio — qué necesita y qué necesita de él.
systemctl list-dependencies nginx systemctl list-dependencies --reverse ssh
📋
journalctl — el sistema de logs de systemd
Consultar, filtrar y seguir los logs del sistema y de cada servicio

journalctl es la herramienta para leer el journal de systemd — un log centralizado y estructurado que recoge mensajes del kernel, del sistema y de todos los servicios. Sustituye a los archivos de log dispersos de antes.

journalctl — todos los filtros importantes
## VER LOGS $ journalctl # todos los logs (paginado con less) $ journalctl -n 50 # últimas 50 líneas $ journalctl -f # follow — ver logs en tiempo real $ journalctl -b # solo logs del boot actual $ journalctl -b -1 # logs del boot anterior ## FILTRAR POR SERVICIO $ journalctl -u nginx # logs de nginx $ journalctl -u nginx -f # logs de nginx en tiempo real $ journalctl -u nginx -n 100 # últimas 100 líneas de nginx $ journalctl -u ssh -u nginx # logs de ssh Y nginx juntos ## FILTRAR POR TIEMPO $ journalctl --since "2025-01-15 10:00:00" $ journalctl --since "1 hour ago" $ journalctl --since yesterday --until today $ journalctl --since "2025-01-15" --until "2025-01-16" ## FILTRAR POR PRIORIDAD (NIVEL) $ journalctl -p err # solo errores (err, crit, alert, emerg) $ journalctl -p warning # advertencias y superiores $ journalctl -b -p err # errores del boot actual ## FILTRAR POR KERNEL $ journalctl -k # solo mensajes del kernel (dmesg) $ journalctl -k --since "10 min ago" ## GESTIÓN DEL JOURNAL $ journalctl --disk-usage # cuánto espacio usan los logs $ sudo journalctl --vacuum-size=500M # reducir logs a máx 500 MB $ sudo journalctl --vacuum-time=30d # eliminar logs de más de 30 días

🟢 El flujo de diagnóstico con journalctl

Cuando un servicio falla, el flujo de diagnóstico es: primero systemctl status nombre para ver el estado y las últimas líneas. Si necesitas más detalle, journalctl -u nombre -n 100 para ver el historial. Si el sistema no arrancó bien, journalctl -b -p err para ver los errores del último boot. Y journalctl -f -u nombre para seguir los logs en tiempo real mientras reproduces el problema.

NivelNúmeroSignificado
emerg0Sistema inutilizable. Fallo catastrófico.
alert1Acción inmediata necesaria.
crit2Condición crítica.
err3Error. El servicio puede seguir corriendo pero con problemas.
warning4Advertencia. Algo inesperado pero no necesariamente un error.
notice5Evento normal pero significativo.
info6Información general del funcionamiento.
debug7Información detallada para depuración.
✏️ Ejercicio del Nivel 17 Sistema

Explora el arranque y los servicios de tu sistema:

  1. UEFI: ejecuta ls /sys/firmware/efi 2>/dev/null && echo "UEFI" || echo "BIOS legacy". ¿En qué modo arrancó tu sistema?
  2. Kernel: ejecuta uname -r y cat /proc/cmdline. ¿Qué versión del kernel tienes? ¿Cuáles son los parámetros de arranque?
  3. systemd targets: ejecuta systemctl get-default. ¿Qué target está activo?
  4. Servicios activos: ejecuta systemctl list-units --type=service --state=running | head -20. ¿Cuántos servicios están corriendo?
  5. Estado de un servicio: ejecuta systemctl status ssh (o sshd en Fedora). ¿Está activo? ¿Habilitado para el arranque?
  6. journalctl: ejecuta journalctl -b -p err. ¿Hay errores en el arranque actual? Luego journalctl -u NetworkManager -n 30.
  7. Crear un servicio: escribe el unit file de ejemplo de la sección Units en /etc/systemd/system/prueba.service, ejecuta sudo systemctl daemon-reload y systemctl status prueba.service.

Análisis de arranque: ejecuta systemd-analyze para ver cuánto tardó el último arranque, y systemd-analyze blame | head -15 para ver qué servicios tardaron más.

🟥 Resumen del Nivel 17

  • Secuencia de arranque: UEFI → GRUB → Kernel+initrd → systemd → Servicios → Display Manager.
  • UEFI es el firmware moderno (reemplaza BIOS), usa partición ESP, soporta Secure Boot y GPT.
  • GRUB muestra el menú de arranque, carga el kernel. Configuración en /etc/default/grub. Aplicar cambios con update-grub.
  • El kernel carga el initrd (RAM disk temporal) para acceder al disco real, luego lanza systemd como PID 1.
  • systemd gestiona el arranque paralelo de servicios mediante unit files (.service, .socket, .timer…).
  • Un unit file tiene secciones [Unit] (descripción/deps), [Service] (cómo ejecutar) y [Install] (cuándo activar).
  • systemctl start/stop/restart/status/enable/disable nombre — la interfaz diaria con los servicios.
  • systemctl daemon-reload — siempre después de crear o modificar un unit file.
  • journalctl — logs centralizados. -u servicio filtra por servicio, -b por boot, -p err por nivel, -f en tiempo real.
  • systemd-analyze blame — identifica qué servicios ralentizan el arranque.
