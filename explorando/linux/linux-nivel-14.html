El modelo de seguridad de Linux
Todo en Linux pertenece a alguien — y eso define quién puede hacer qué

Linux fue diseñado desde sus inicios como un sistema multiusuario. Cada recurso del sistema — archivos, procesos, dispositivos, sockets de red — pertenece a un usuario y a un grupo. El kernel comprueba esta propiedad en cada operación y decide si la permite o la deniega.

🏢 Analogía — El edificio de apartamentos con conserje

Linux es como un edificio de apartamentos: cada apartamento (/home/hugo) pertenece a su inquilino (usuario). El propietario puede entrar cuando quiere, modificar su apartamento, invitar a gente. Los vecinos no pueden entrar a tu apartamento sin permiso. El conserje (root) tiene llave maestra de todos los apartamentos y puede entrar a cualquiera en caso de emergencia. Cada puerta tiene una lista de quién puede entrar, ver o modificar qué (permisos rwx).

# El modelo de tres capas de permisos en Linux Cada archivo o directorio tiene: Propietario (owner) → el usuario que lo creó o al que se asignó Grupo (group) → un grupo de usuarios con acceso especial Otros (others) → todos los demás usuarios del sistema Y tres tipos de permiso por capa: r (read) → leer el contenido w (write) → modificar/eliminar x (execute) → ejecutar (archivos) / acceder (directorios) # Resultado: 9 bits de permiso por archivo rwxr-xr-- owner group other

Usuarios en Linux
/etc/passwd, UID, tipos de usuario y comandos de gestión

Cada usuario en Linux tiene un UID (User ID) único — un número que el kernel usa internamente. Los nombres de usuario son solo una interfaz amigable para los humanos. Los usuarios se almacenan en /etc/passwd.

👑
root (UID 0)
El superusuario. Puede hacer absolutamente todo. UID siempre 0. En Ubuntu está desactivado por defecto — se usa sudo.
👤
Usuario normal (UID ≥1000)
Los usuarios humanos. Creados al instalar el SO o con adduser. Tienen home en /home/usuario. UIDs desde 1000.
🤖
Usuario de sistema (UID 1-999)
Creados para servicios: www-data (nginx), postgres, mysql, nobody. Sin contraseña, sin home real, sin login interactivo.
/etc/passwd y gestión de usuarios
# Ver el archivo /etc/passwd — un usuario por línea $ cat /etc/passwd | head -5 root:x:0:0:root:/root:/bin/bash daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin hugo:x:1000:1000:Hugo,,,:/home/hugo:/bin/bash # formato: usuario:x:UID:GID:comentario:home:shell # la 'x' significa que la contraseña está en /etc/shadow (encriptada) # Ver tu UID, GID y grupos actuales $ id uid=1000(hugo) gid=1000(hugo) grupos=1000(hugo),4(adm),24(cdrom),27(sudo) # Ver quién está conectado al sistema ahora $ who hugo tty7 2025-01-15 09:45 (:0) # Crear usuario nuevo $ sudo adduser maria # interactivo — pide nombre, contraseña, etc. $ sudo useradd -m -s /bin/bash carlos # rápido con flags # Cambiar contraseña $ passwd # cambia TU contraseña $ sudo passwd maria # root cambia la de maria # Eliminar usuario $ sudo deluser maria # elimina usuario pero mantiene home $ sudo deluser --remove-home maria # elimina también /home/maria # Cambiar de usuario $ su - maria # cambia a maria (pide contraseña de maria) $ exit # vuelve al usuario anterior

Grupos — permisos compartidos
Cómo organizar usuarios con acceso compartido a recursos

Un grupo es una colección de usuarios que comparten permisos. Cada archivo tiene un grupo propietario, y todos los miembros de ese grupo tienen los permisos del grupo sobre ese archivo. Los grupos se almacenan en /etc/group.

grupos — gestión completa
# Ver los grupos del sistema $ cat /etc/group | head -8 root:x:0: sudo:x:27:hugo docker:x:998:hugo www-data:x:33: # Ver tus grupos $ groups hugo adm cdrom sudo plugdev lpadmin sambashare # Añadir usuario a un grupo $ sudo usermod -aG docker hugo # -a = append, -G = grupo $ sudo usermod -aG sudo maria # dar permisos sudo a maria # IMPORTANTE: cerrar sesión y volver para que tenga efecto # Crear y eliminar grupos $ sudo groupadd desarrolladores $ sudo groupdel desarrolladores # Ver a qué grupos pertenece un usuario $ id hugo uid=1000(hugo) gid=1000(hugo) grupos=1000(hugo),27(sudo),998(docker)

🟢 Grupos importantes que deberías conocer

  • sudo — permite usar sudo (equivalente a administradores en Windows)
  • docker — permite usar Docker sin sudo
  • www-data — el grupo del servidor web (nginx/apache)
  • adm — permite leer logs del sistema en /var/log
  • dialout — acceso a puertos seriales (Arduino, Raspberry Pi)
  • video/audio — acceso a GPU y dispositivos de audio
🔐
Permisos rwx — leer, escribir, ejecutar
Descifrar el código de permisos que muestra ls -l

Cuando ejecutas ls -l ves algo como -rwxr-xr--. Esos 10 caracteres contienen toda la información de permisos de un archivo. Aprender a leerlos e interpretarlos es fundamental.

Ejemplo: -rwxr-xr-- 1 hugo developers 4521 jan 15 index.sh
- rwx r-x r-- 1 hugo developers 4521 jan 15 index.sh
- = tipo (- archivo, d directorio, l symlink, b dispositivo bloque)
rwx = owner (hugo) puede leer, escribir y ejecutar
r-x = group (developers) puede leer y ejecutar, NO escribir
r-- = others (todos los demás) solo puede leer

¿Qué significa cada permiso en archivos vs directorios?

PermisoEn archivosEn directorios
r (read)Leer el contenido del archivo (cat, less)Listar el contenido del directorio (ls)
w (write)Modificar o eliminar el archivoCrear, renombrar o eliminar archivos dentro del directorio
x (execute)Ejecutar el archivo como programa (./script.sh)Acceder al directorio (cd) y a sus archivos por ruta

💡 x en directorios — el más confuso

El permiso x en un directorio no significa "ejecutar" sino atravesar — poder hacer cd en él y acceder a los archivos que contiene por ruta. Puedes tener r sin x: ves los nombres de los archivos con ls pero no puedes abrirlos. O x sin r: puedes acceder a los archivos si sabes el nombre, pero ls no te mostrará nada.

leer permisos con ls -l
$ ls -la ~/proyectos total 32 drwxr-xr-x 4 hugo hugo 4096 jan 15 10:23 . drwxr-x--- 18 hugo hugo 4096 jan 15 09:45 .. -rw-r--r-- 1 hugo hugo 4521 jan 14 15:30 README.md -rwxr-xr-x 1 hugo hugo 892 jan 13 11:20 deploy.sh drwxrwxr-x 2 hugo devs 4096 jan 15 10:10 shared/ -rw------- 1 hugo hugo 1024 jan 10 08:00 .env # ↑ .env solo lo puede leer/escribir el propietario (secretos) # Tipos de archivo en el primer carácter: # - → archivo regular # d → directorio # l → symlink # b → dispositivo de bloque (disco) # c → dispositivo de carácter (terminal)
⚙️
chmod — cambiar permisos
Modo simbólico y modo octal — las dos formas de cambiar permisos

chmod (CHange MODe) cambia los permisos de un archivo o directorio. Tiene dos formas de especificar los permisos: simbólica (más legible) y octal (más concisa y común en la práctica).

Modo simbólico — intuitivo

chmod simbólico — u/g/o/a + r/w/x
# Sintaxis: chmod [quién][+/-/=][qué] archivo # quién: u=owner g=group o=others a=all # operador: + añadir - quitar = establecer exactamente # qué: r=read w=write x=execute # Dar permiso de ejecución al propietario $ chmod u+x script.sh # Dar permiso de ejecución a todos $ chmod a+x script.sh # Quitar permiso de escritura al grupo y a otros $ chmod go-w archivo.txt # Establecer permisos exactos para cada capa $ chmod u=rwx,g=r-x,o=r-- script.sh # Aplicar recursivamente a un directorio $ chmod -R 755 /var/www/html/

Modo octal — el más usado en la práctica

Cada permiso (r=4, w=2, x=1) se suma para cada capa. El resultado es un número de 3 dígitos (owner, group, others).

Owner

4+2+1 = 7
Group

5
4+0+1 = 5

OctalSimbólicoUso típico
777rwxrwxrwxTodos pueden todo. Solo para /tmp. Nunca en producción.
755rwxr-xr-xEjecutables y directorios públicos. Estándar en /usr/bin.
644rw-r--r--Archivos de configuración, HTML, código fuente. El más común.
600rw-------Archivos privados: .env, claves SSH, ~/.ssh/id_rsa.

640rw-r-----Owner lee/escribe, grupo solo lee, otros nada. Logs.
400r--------Solo lectura para el propietario. Claves SSH públicas.
chmod octal — los más usados
# El script necesita ser ejecutable $ chmod 755 deploy.sh # El .env solo lo lee el propietario $ chmod 600 .env # Los archivos web son legibles por el servidor $ chmod 644 index.html # La clave SSH privada debe ser 600 o SSH rechaza la conexión $ chmod 600 ~/.ssh/id_rsa $ chmod 644 ~/.ssh/id_rsa.pub # Aplicar 755 a todos los directorios y 644 a todos los archivos $ find /var/www/html -type d -exec chmod 755 {} \; $ find /var/www/html -type f -exec chmod 644 {} \;
👤
chown y chgrp — cambiar propietario y grupo
Asignar la propiedad correcta a archivos y directorios
chown — cambiar propietario
# Sintaxis: chown [usuario][:grupo] archivo # Cambiar solo el propietario $ sudo chown hugo archivo.txt # Cambiar propietario Y grupo a la vez $ sudo chown hugo:developers archivo.txt # Cambiar solo el grupo (con chown) $ sudo chown :www-data /var/www/html/ # chgrp — comando específico para cambiar grupo $ sudo chgrp www-data /var/www/html/ # Recursivo — cambia propietario de directorio y todo su contenido $ sudo chown -R hugo:hugo ~/proyectos/ # Caso típico: dar un proyecto web al servidor nginx $ sudo chown -R www-data:www-data /var/www/html/ $ sudo chmod -R 755 /var/www/html/ # Verificar el resultado $ ls -la /var/www/html/ drwxr-xr-x 3 www-data www-data 4096 jan 15 index.html

📌 El patrón típico en servidores web

En un servidor nginx/apache: los archivos pertenecen a www-data:www-data (el usuario del servidor web) con permisos 644 para archivos y 755 para directorios. El desarrollador (hugo) está en el grupo www-data para poder editar los archivos. Así el servidor puede leerlos y el desarrollador puede modificarlos.

🦸
sudo — ejecutar como root sin ser root
El mecanismo de elevación de privilegios más importante de Linux

sudo (Superuser DO) permite a usuarios autorizados ejecutar comandos con privilegios de root sin necesidad de conocer la contraseña de root. Es mucho más seguro que usar la cuenta root directamente.

🔑 Analogía — El poder notarial temporal

sudo es como un poder notarial temporal y auditado. El notario (root) no está presente en cada operación — le da a personas de confianza (usuarios en el grupo sudo) la capacidad de actuar en su nombre para tareas específicas. Cada uso queda registrado en el log. Si algo sale mal, hay un rastro completo de quién hizo qué y cuándo.

sudo — uso y configuración
# Ejecutar un comando como root $ sudo apt update [sudo] password for hugo: **** Hit:1 http://archive.ubuntu.com/ubuntu noble InRelease # sudo recuerda la contraseña por 15 minutos (configurable) # El próximo sudo en esos 15 min no pide contraseña # Abrir una shell completa como root $ sudo -i # shell de root con su entorno $ sudo -s # shell de root con tu entorno actual # ¡Cuidado! Sal con exit cuando termines # Ver qué puede hacer tu usuario con sudo $ sudo -l User hugo may run the following commands on ubuntu: (ALL : ALL) ALL # Ejecutar el último comando con sudo (si olvidaste el sudo) $ apt update # error: permiso denegado $ sudo !! # ejecuta: sudo apt update # Ver el log de sudo (quién hizo qué) $ sudo cat /var/log/auth.log | grep sudo | tail -10 jan 15 10:23:45 ubuntu sudo: hugo : TTY=pts/0 ; COMMAND=/usr/bin/apt update

El archivo /etc/sudoers

El archivo /etc/sudoers define exactamente quién puede usar sudo y para qué. Nunca lo edites directamente — usa visudo que valida la sintaxis antes de guardar.

# /etc/sudoers — fragmento típico # Root puede hacer todo root ALL=(ALL:ALL) ALL # Miembros del grupo sudo pueden hacer todo %sudo ALL=(ALL:ALL) ALL # Hugo puede reiniciar nginx sin contraseña hugo ALL=(ALL) NOPASSWD: /bin/systemctl restart nginx # El usuario deploy solo puede actualizar el código deploy ALL=(ALL) NOPASSWD: /usr/bin/git pull, /bin/systemctl restart app # Editar siempre con visudo — nunca con nano/vim directamente # $ sudo visudo
SUDOERS

⚠️ sudo vs su vs login como root

sudo es la forma recomendada — queda auditado, tiene timeout, y el usuario mantiene su identidad. su - (Switch User) cambia completamente a otro usuario — necesitas la contraseña de ese usuario. Loguearse directamente como root es la peor opción — sin auditoría, sin timeout, máximo riesgo. En Ubuntu, la cuenta root está deshabilitada por defecto precisamente para forzar el uso de sudo.

Permisos especiales — SUID, SGID y Sticky Bit
Los tres bits de permiso avanzados que van más allá de rwx

Además de rwx, Linux tiene tres bits de permiso especiales que modifican el comportamiento de ejecución y acceso. Son menos comunes en el día a día pero críticos para entender cómo funciona el sistema.

BitEn archivosEn directoriosCómo se muestra
SUID (4xxx)El archivo se ejecuta con los permisos del propietario, no del usuario que lo ejecuta. Ej: /usr/bin/passwd se ejecuta como root aunque lo lance un usuario normal.Sin efecto significativo-rwsr-xr-x (s en posición x del owner)
SGID (2xxx)Se ejecuta con los permisos del grupo propietarioLos archivos creados dentro heredan el grupo del directorio, no el grupo del creadordrwxr-sr-x (s en posición x del group)
Sticky Bit (1xxx)Sin efecto en archivos modernosSolo el propietario de un archivo puede borrarlo, aunque otros tengan w en el directorio. Usado en /tmpdrwxrwxrwt (t en posición x de others)
permisos especiales en el sistema
# Ver archivos con SUID en el sistema (se ejecutan como root) $ find /usr/bin -perm -4000 2>/dev/null /usr/bin/passwd /usr/bin/sudo /usr/bin/su /usr/bin/mount # passwd tiene SUID — por eso un usuario normal puede cambiar su contraseña # (las contraseñas están en /etc/shadow que solo root puede escribir) $ ls -la /usr/bin/passwd -rwsr-xr-x 1 root root 59976 /usr/bin/passwd # ↑ la 's' indica SUID — corre como root siempre # /tmp tiene sticky bit — cada uno borra solo lo suyo $ ls -la / | grep tmp drwxrwxrwt 1 root root 4096 /tmp # ↑ la 't' indica sticky bit # Aplicar sticky bit a un directorio compartido $ sudo chmod +t /compartido/ # o en octal: $ sudo chmod 1777 /compartido/
✏️ Ejercicio del Nivel 14 Seguridad

Practica el sistema de permisos completo:

  1. Usuarios: ejecuta id — anota tu UID, GID y todos tus grupos. ¿Estás en el grupo sudo?
  2. Leer permisos: ejecuta ls -la ~ y descifra los permisos de 5 archivos distintos. ¿Qué puede hacer cada capa?
  3. chmod: crea touch ~/test-permisos.sh. Ejecuta ls -la ~/test-permisos.sh. ¿Tiene x? Añádelo: chmod u+x ~/test-permisos.sh. Verifica de nuevo.
  4. Octal: aplica chmod 644 ~/test-permisos.sh. ¿Qué permisos tiene ahora? Luego chmod 700 ~/test-permisos.sh. ¿Y ahora?
  5. SUID: ejecuta ls -la /usr/bin/passwd. ¿Ves la 's' en los permisos del owner? ¿Por qué es importante?
  6. sudo: ejecuta sudo -l — ¿qué comandos puedes usar con sudo?
  7. Grupos: ejecuta groups. ¿Estás en el grupo docker? Si no: sudo usermod -aG docker $USER y cierra/abre sesión.

Escenario práctico: Tienes un proyecto web en ~/mi-web/ y quieres que nginx pueda leerlo. Ejecuta: sudo chown -R $USER:www-data ~/mi-web/ && chmod -R 750 ~/mi-web/. ¿Por qué 750 y no 755?

🟥 Resumen del Nivel 14

  • Linux es multiusuario: cada archivo tiene propietario, grupo y permisos para otros.
  • UID 0 = root, UID 1-999 = usuarios de sistema, UID ≥1000 = usuarios humanos.
  • /etc/passwd lista usuarios. /etc/group lista grupos. /etc/shadow guarda contraseñas encriptadas.
  • Permisos: r=4 (leer), w=2 (escribir), x=1 (ejecutar/atravesar). Se aplican a owner, group y others.
  • chmod 755 archivo — owner todo, grupo y otros solo leer/ejecutar. El más común para ejecutables.
  • chmod 644 archivo — owner leer/escribir, todos los demás solo leer. El más común para archivos.
  • chown usuario:grupo archivo cambia el propietario. chown -R aplica recursivamente.
  • sudo ejecuta comandos como root con auditoría y timeout. Mucho mejor que loguearse como root.
  • SUID — el ejecutable corre con los permisos del propietario (ej: passwd corre como root). Sticky bit — en /tmp, cada usuario solo borra sus propios archivos.
