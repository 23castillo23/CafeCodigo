CPU — monitorizar el procesador
Núcleos, frecuencia, uso por núcleo y el governor de energía

El procesador es el recurso más contendido del sistema — múltiples procesos compiten por tiempo de CPU. Linux expone información detallada de la CPU en tiempo real a través de /proc/cpuinfo, /sys/ y herramientas de monitorización.

información y monitorización de CPU
# Info básica del procesador $ lscpu Architecture: x86_64 CPU(s): 12 Thread(s) per core: 2 Core(s) per socket: 6 Model name: Intel Core i7-10750H @ 2.60GHz CPU MHz: 2600.000 CPU max MHz: 5000.000 L3 cache: 12288K # Ver uso de CPU por núcleo en tiempo real (en top) $ top # luego pulsa '1' para ver cada núcleo # mpstat — estadísticas detalladas por núcleo $ sudo apt install sysstat $ mpstat -P ALL 2 # actualiza cada 2 segundos CPU %usr %sys %iowait %idle all 8.2 2.1 0.3 89.4 0 12.5 3.2 0.0 84.3 1 4.8 1.2 0.8 93.2 # Ver la frecuencia actual de cada núcleo $ cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq | head -6 2600000 4200000 # En Hz — divide entre 1000 para MHz # Governor de energía — política de frecuencia de CPU $ cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor powersave # powersave = ahorra energía performance = máxima frecuencia siempre # Cambiar governor (temporal) $ echo "performance" | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor # O con herramienta: $ sudo apt install cpufrequtils $ sudo cpufreq-set -g performance
GovernorComportamientoMejor para
powersaveFrecuencia mínima siempre. Ahorra mucha batería.Laptops en batería, servidores con poca carga
ondemandSube la frecuencia cuando hay carga, baja cuando hay idle.Uso general de escritorio
performanceFrecuencia máxima siempre. Máximo rendimiento.Gaming, compilación, cargas intensas
schedutilBasado en el scheduler del kernel. Moderno y eficiente.Por defecto en kernels modernos
conservativeComo ondemand pero sube y baja más gradualmente.Laptops con batería limitada

🟢 turbostat — ver el estado real de la CPU

turbostat (parte de linux-tools) muestra en tiempo real la frecuencia real de cada núcleo, temperatura, consumo de energía y estado de bajo consumo (C-states). Es la herramienta más detallada para entender qué hace realmente la CPU: sudo apt install linux-tools-common linux-tools-$(uname -r) && sudo turbostat.

RAM — cómo Linux gestiona la memoria
free, /proc/meminfo, caché, swap y el OOM killer

Linux gestiona la RAM de forma agresiva y eficiente: usa toda la RAM disponible para cachear datos del disco (page cache), lo que hace que el sistema sea más rápido. La RAM "libre" en Linux casi siempre aparece muy baja — eso es normal y deseable.

🗄️ Analogía — El escritorio del empleado eficiente

Un empleado eficiente no deja el escritorio vacío — mantiene sobre él todos los documentos que ha usado recientemente por si los necesita de nuevo. Linux hace lo mismo: usa la RAM libre como caché del disco. Si un proceso necesita más RAM, Linux desaloja la caché más antigua para dársela. La RAM "libre" en Linux es RAM disponible para caché — no RAM desperdiciada.

monitorizar la RAM en profundidad
# free — la vista rápida de RAM y swap $ free -h total used free shared buff/cache available Mem: 15Gi 4.8Gi 1.2Gi 312Mi 9.0Gi 10Gi Swap: 8Gi 0B 8Gi # "available" es lo que realmente importa — lo que queda para apps nuevas # buff/cache = RAM usada como caché (liberable si hace falta) # /proc/meminfo — desglose completo $ cat /proc/meminfo | head -20 MemTotal: 16189208 kB ← RAM total MemFree: 1234567 kB ← libre real MemAvailable: 10234567 kB ← disponible para apps (la importante) Buffers: 234567 kB ← cache de metadatos del FS Cached: 8765432 kB ← page cache (datos de disco en RAM) SwapTotal: 8388608 kB SwapFree: 8388608 kB ← swap sin usar = buen signo Dirty: 4567 kB ← datos en RAM pendientes de escribir a disco # Ver el uso de RAM por proceso $ ps aux --sort=-%mem | head -8 USER PID %CPU %MEM VSZ RSS COMMAND hugo 1847 3.2 8.4 3856204 685892 firefox hugo 2341 1.1 5.2 2341568 424960 code # smem — reporte de memoria más preciso (sin doble contar shared) $ sudo apt install smem $ smem -s pss -r | head -10 # Forzar al kernel a liberar la caché de página (raramente necesario) $ sudo sync && echo 3 | sudo tee /proc/sys/vm/drop_caches # Monitorizar el swap en tiempo real $ watch -n 1 free -h

💡 El OOM Killer — Linux cuando se queda sin RAM

Si el sistema se queda sin RAM y sin swap, el kernel activa el OOM Killer (Out Of Memory Killer). El OOM Killer elige el proceso más "caro" para matar — normalmente el que usa más RAM y tiene menor prioridad. Puedes ver si ha matado procesos con dmesg | grep -i "oom" o journalctl -k | grep -i oom. Ver el OOM Killer actuar es señal clara de que necesitas más RAM o menos procesos.

available
El valor real de RAM libre
free -h
SwapFree
Si se usa swap, el sistema va lento
free -h / swapon -s
Dirty
Datos en RAM sin escribir al disco
cat /proc/meminfo
VSZ vs RSS
Virtual vs real en RAM (RSS importa)
ps aux

Load Average — la carga del sistema
Qué significan esos tres números y cuándo preocuparse

El load average es una de las métricas más importantes de Linux. Aparece en top, uptime y htop como tres números. Representa el número promedio de procesos en estado R (ejecutándose) o D (esperando I/O) durante el último 1, 5 y 15 minutos.

🛣️ Analogía — Los carriles de una autopista

El load average es como contar coches en una autopista. Si tu CPU tiene 4 núcleos, la autopista tiene 4 carriles. Un load de 4.0 significa que todos los carriles están llenos — el sistema está al 100% de capacidad. Un load de 2.0 en una CPU de 4 núcleos significa que solo el 50% de la capacidad está usada — bien. Un load de 8.0 en 4 núcleos significa que hay el doble de coches que carriles — hay cola, el sistema está sobrecargado.

load average — leer e interpretar
# Ver el load average $ uptime 10:45:32 up 1:23, 1 user, load average: 1.42, 0.98, 0.75 # ↑1min ↑5min ↑15min $ cat /proc/loadavg 1.42 0.98 0.75 3/287 14923 # 3/287 = 3 procesos corriendo de 287 totales # 14923 = último PID asignado # Número de núcleos para interpretar el load $ nproc 12 # Con 12 núcleos: load de 1.42 = 12% de uso → muy bien # Con 2 núcleos: load de 1.42 = 71% de uso → aceptable # Si load > nproc → sistema sobrecargado → investigar # sar — historial de carga (del paquete sysstat) $ sar -q 1 5 # muestra load cada segundo, 5 veces $ sar -u 1 5 # uso de CPU cada segundo
# Interpretar el load average según los núcleos Sistema con 4 núcleos: load 0.5 → excelente — 12% de uso load 2.0 → bien — 50% de uso load 4.0 → límite — 100% de uso, no hay cola load 6.0 → sobrecargado — hay cola, 50% de procesos esperando load 12.0 → crítico — triplicado, investigar urgente # La tendencia importa más que el valor instantáneo: 1.42, 0.98, 0.75 → bajando — el pico pasó, el sistema se recupera 0.75, 0.98, 1.42 → subiendo — el problema está creciendo, actúa ahora

I/O de disco — el cuello de botella más común
iostat, iotop y cómo identificar qué proceso está saturando el disco

El disco es casi siempre el componente más lento del sistema — órdenes de magnitud más lento que la RAM o la CPU. Un sistema con CPU ociosa pero disco saturado se siente igualmente lento. Los procesos en estado D (Disk Sleep) son la señal.

monitorizar el I/O de disco
# iostat — estadísticas de I/O por dispositivo $ iostat -xh 2 # actualiza cada 2 segundos, formato human-readable Device r/s w/s rMB/s wMB/s await %util sda 12.3 45.2 0.8 3.2 4.2 23.5 nvme0 88.4 234.1 6.3 18.7 0.3 8.2 # %util → porcentaje de tiempo que el disco está ocupado # await → tiempo promedio de espera en ms (debería ser <10ms SSD, <50ms HDD) # iotop — qué proceso usa más I/O (como top pero para disco) $ sudo apt install iotop $ sudo iotop $ sudo iotop -o # -o = solo muestra procesos con I/O activo TID PRIO USER DISK READ DISK WRITE COMMAND 2341 BE/4 hugo 0.00 B/s 4.23 M/s code 847 BE/4 root 1.24 M/s 0.00 B/s updatedb # /proc/diskstats — estadísticas en bruto del kernel $ cat /proc/diskstats | grep nvme0 # Ver velocidades de lectura/escritura del disco $ sudo hdparm -t /dev/sda # velocidad de lectura secuencial Timing buffered disk reads: 402 MB in 3.01 seconds = 133.60 MB/sec # Benchmark rápido de escritura/lectura con dd $ dd if=/dev/zero of=/tmp/test bs=1G count=1 oflag=direct 1073741824 bytes copied, 3.21 s, 334 MB/s $ dd if=/tmp/test of=/dev/null bs=1G count=1 iflag=direct 1073741824 bytes copied, 2.87 s, 374 MB/s $ rm /tmp/test

Temperatura y throttling térmico
sensors, lm-sensors y cómo el calor afecta al rendimiento

Cuando una CPU o GPU supera su temperatura máxima segura, el sistema activa el thermal throttling — reduce automáticamente la frecuencia para bajar la temperatura. Un sistema que "va lento" a veces es simplemente un sistema que tiene demasiado calor.

monitorizar temperaturas
# lm-sensors — temperaturas de CPU, GPU y placa base $ sudo apt install lm-sensors $ sudo sensors-detect # detectar sensores disponibles (solo una vez) $ sensors coretemp-isa-0000 Core 0: +52.0°C (high = +100.0°C, crit = +100.0°C) Core 1: +49.0°C Core 2: +53.0°C acpitz-acpi-0 temp1: +47.0°C # watch sensors — actualizar en tiempo real $ watch -n 1 sensors # Temperatura de los discos (SMART) $ sudo apt install smartmontools $ sudo smartctl -A /dev/sda | grep -i temp 190 Airflow_Temperature_Cel 0x0022 070 049 045 Old_age Always - 30 # Ver si hay throttling térmico en el kernel $ dmesg | grep -i "thermal\|throttl" [ 1234.567] CPU0: Core temperature above threshold, cpu clock throttled # Temperatura de GPU NVIDIA $ nvidia-smi --query-gpu=temperature.gpu --format=csv,noheader 67 # Temperatura de GPU AMD $ sensors | grep -i "edge\|junction"

Benchmarks rápidos desde la terminal
Medir el rendimiento real de CPU, RAM y disco sin instalar suites complejas
sysbench — CPU y RAM
Benchmark rápido de CPU con cálculo de números primos. También RAM y MySQL.
sudo apt install sysbench sysbench cpu --threads=$(nproc) run sysbench memory run
stress — generar carga
Saturar CPU, RAM o disco para comprobar estabilidad o el comportamiento térmico.
sudo apt install stress stress --cpu 8 --timeout 60s stress --vm 2 --vm-bytes 1G --timeout 30s
fio — benchmark de disco
El estándar para medir IOPS, latencia y throughput de un disco o SSD.
sudo apt install fio fio --name=test --rw=read \ --bs=4k --numjobs=4 \ --filename=/tmp/fiotest \ --size=1G --runtime=30
time — medir un comando
Medir cuánto tarda en ejecutarse cualquier comando — CPU real vs user vs sys.
time make -j$(nproc) time python3 script.py time tar -czf backup.tar.gz ~/
perf — profiling de CPU
Herramienta del kernel para profiling avanzado. Ver dónde gasta tiempo la CPU.
sudo apt install linux-perf perf top # top por funciones perf stat ./programa # estadísticas del programa
speedtest-cli
Medir la velocidad de red desde la terminal — útil para comparar con el disco local.
sudo apt install speedtest-cli speedtest-cli

Flujo de diagnóstico — el sistema va lento
La metodología sistemática para encontrar el cuello de botella

Cuando el sistema va lento, la pregunta es siempre: ¿lento en qué? CPU, RAM, disco o red son los candidatos. Este flujo de diagnóstico te lleva del síntoma al culpable en minutos.

1
Comprobar la carga general
uptime | top | htop
¿Es el load average mayor que el número de núcleos? Si es alto → hay procesos compitiendo. Si es bajo → el cuello de botella no es la CPU.
2
Ver qué proceso consume más CPU
ps aux --sort=-%cpu | head -8
¿Hay un proceso al 100%? ¿Es esperado (compilando) o inesperado (malware, loop infinito)? ¿Muchos procesos en estado D? → problema de I/O.
3
Comprobar la RAM
free -h
¿El valor "available" es muy bajo (< 200 MB)? ¿Se está usando swap? Si el swap está activo, la RAM está agotada y el sistema paginará — muy lento.
4
Comprobar el disco
iostat -xh 2 | sudo iotop -o
¿El %util del disco está al 100%? ¿El await es alto? ¿iotop muestra un proceso con I/O masivo? → el disco es el cuello de botella.
5
Comprobar temperatura
sensors | watch -n 1 sensors
CPU > 90°C, GPU > 85°C → hay throttling térmico. La CPU reduce su frecuencia para no quemarse. Revisar ventilación, pasta térmica y ventiladores.
6
Revisar logs de errores
journalctl -b -p err | dmesg | grep -i error
¿Hay errores de hardware? ¿Errores de disco (I/O error, EXT4-fs error)? ¿OOM killer activo? Los logs revelan problemas que las métricas no muestran.

Optimizaciones prácticas
Ajustes concretos para hacer Linux más rápido y eficiente
optimizaciones prácticas
## SWAP — ajustar swappiness (cuándo Linux empieza a usar swap) $ cat /proc/sys/vm/swappiness 60 # 60 = valor por defecto. 0-100. Más bajo = usa menos swap # Para sistemas con mucha RAM, bajar a 10: $ sudo sysctl vm.swappiness=10 # Para hacerlo permanente: $ echo "vm.swappiness=10" | sudo tee -a /etc/sysctl.conf ## SSD — habilitar TRIM para mantener el rendimiento $ sudo systemctl enable fstrim.timer # ejecuta TRIM semanalmente $ sudo fstrim -v / # ejecutar TRIM ahora ## ARRANQUE — identificar y deshabilitar servicios lentos $ systemd-analyze blame | head -15 # servicios que tardan más en arrancar $ sudo systemctl disable bluetooth # si no usas bluetooth $ sudo systemctl disable cups # si no usas impresoras ## OOM — ajustar cuándo mata procesos el OOM killer # Proteger un proceso crítico del OOM killer (ej: postgres) $ echo -1000 | sudo tee /proc/$(pidof postgres)/oom_score_adj ## PRELOAD — precargar apps frecuentes en RAM $ sudo apt install preload # aprende tus patrones y precarga apps ## TRANSPARENT HUGEPAGES — mejora el rendimiento con bases de datos $ cat /sys/kernel/mm/transparent_hugepage/enabled [always] madvise never # Para bases de datos (MongoDB, Redis) mejor "madvise" o "never": $ echo "madvise" | sudo tee /sys/kernel/mm/transparent_hugepage/enabled ## I/O SCHEDULER — cambiar el schedulador del disco $ cat /sys/block/nvme0n1/queue/scheduler [none] mq-deadline kyber bfq # Para SSDs: "none" o "mq-deadline" es óptimo # Para HDDs: "bfq" da mejor rendimiento interactivo

🟢 La regla de oro de la optimización

Nunca optimices sin medir primero. El proceso es: medir → identificar el cuello de botella → aplicar UN cambio → medir de nuevo. Cambiar varias cosas a la vez impide saber qué ayudó y qué no. La mayoría de los sistemas Linux modernos ya están bien configurados por defecto — los casos donde optimizaciones manuales marcan una diferencia real son instalaciones de servidor bajo cargas específicas.

✏️ Ejercicio del Nivel 19 Diagnóstico

Haz un diagnóstico completo del rendimiento de tu sistema:

  1. CPU: ejecuta lscpu | grep -E "CPU\(s\)|Thread|Model name|MHz". ¿Cuántos núcleos reales tienes? ¿Cuántos hilos?
  2. Load: ejecuta uptime. ¿Cuál es el load average? ¿Es mayor o menor que tu número de núcleos (nproc)?
  3. RAM: ejecuta free -h. ¿Cuánta RAM "available" tienes? ¿Se está usando swap? ¿Cuánto buff/cache hay?
  4. RAM por proceso: ejecuta ps aux --sort=-%mem | head -6. ¿Qué proceso consume más memoria?
  5. Temperatura: instala lm-sensors (sudo apt install lm-sensors && sudo sensors-detect --auto) y ejecuta sensors. ¿Cuál es la temperatura de tu CPU?
  6. Benchmark CPU: ejecuta time dd if=/dev/zero bs=1M count=1024 | md5sum. ¿Cuánto tarda en procesar 1 GB?
  7. Benchmark disco: ejecuta dd if=/dev/zero of=/tmp/test bs=1G count=1 oflag=direct && rm /tmp/test. ¿A qué velocidad escribe tu disco?

Análisis: con los datos recopilados, identifica el componente más lento de tu sistema. ¿CPU, RAM o disco? ¿Hay algún proceso que esté consumiendo recursos de forma desproporcionada?

🟥 Resumen del Nivel 19

  • lscpu — info completa de la CPU. mpstat -P ALL — uso por núcleo. Governor: powersave (batería) vs performance (máximo rendimiento).
  • free -h — el valor available es la RAM real disponible. buff/cache es caché desalojable — no es RAM perdida.
  • Si swap se usa activamente, la RAM está agotada y el sistema irá lento. Aumentar RAM o reducir procesos.
  • El OOM Killer mata procesos cuando se agota toda la memoria. dmesg | grep oom para detectarlo.
  • Load average con 3 valores (1/5/15 min). Si es mayor que nproc → sobrecargado. Si la tendencia sube → actúa ahora.
  • iostat -xh 2 — rendimiento del disco. sudo iotop -o — qué proceso hace más I/O. Muchos procesos en estado D → I/O saturado.
  • sensors — temperaturas en tiempo real. Si la CPU supera su Tjmax → throttling térmico → rendimiento reducido automáticamente.
  • Flujo de diagnóstico: uptime → ps CPU → free RAM → iostat disco → sensors temperatura → journalctl errores.
  • Optimizaciones clave: swappiness=10 con mucha RAM, fstrim semanal en SSD, deshabilitar servicios no usados en el arranque.
