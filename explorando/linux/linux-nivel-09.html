Visión general — las 6 capas
El mapa completo de cómo se organiza un sistema Linux por dentro

Linux no es un bloque monolítico — es un sistema perfectamente estratificado en capas donde cada una tiene una responsabilidad clara y solo se comunica con las capas adyacentes. Entender este modelo es el salto conceptual que separa a quien "usa Linux" de quien "entiende Linux".

🏢 Analogía — El edificio de oficinas

Linux es como un edificio de oficinas de 6 plantas. La planta baja es el hardware — los cimientos físicos. La primera planta es el kernel — seguridad, control de acceso, gestión de recursos. Las plantas intermedias son los servicios del sistema. La última planta son las apps que el usuario ve. Cada planta accede a la de abajo mediante ascensores controlados (las System Calls) — nadie puede saltar pisos ni acceder directamente al sótano sin pasar por seguridad.

💡 La regla fundamental: cada capa solo habla con sus vecinas

Firefox no habla directamente con el disco. glibc no habla directamente con la GPU. Cada capa usa los servicios de la capa inmediatamente inferior y ofrece servicios a la inmediatamente superior. Esta separación es lo que hace que Linux sea seguro, estable y modular — un bug en Firefox no puede corromper el kernel.

Capa 1 — Hardware
Los componentes físicos y cómo el kernel los ve

El hardware es la base de todo. Linux lo abstrae en categorías de dispositivos para que las capas superiores no tengan que saber si el disco es un Samsung SSD NVMe o un disco duro Seagate de 2007 — ambos aparecen como /dev/sda o /dev/nvme0n1.

CPU
El kernel ve núcleos, hilos, caché y frecuencia. Asigna tiempo de CPU a los procesos mediante el scheduler CFS (Completely Fair Scheduler).
RAM
El kernel gestiona páginas de 4KB. Cada proceso cree tener toda la RAM (memoria virtual). El kernel mapea páginas virtuales a físicas.
Almacenamiento
SSD, HDD, NVMe aparecen como dispositivos de bloques en /dev/. El kernel usa drivers específicos para cada tipo de controladora.
Red (NIC)
La tarjeta de red aparece como interfaz (eth0, wlan0). El stack de red del kernel gestiona TCP/IP, paquetes y buffers.
GPU
La más compleja. Drivers (NVIDIA, AMD, Intel) exponen la GPU al sistema. DRM/KMS gestiona el display. Vulkan/OpenGL para renderizado.
Dispositivos USB/HID
Teclado, ratón, USB — el subsistema udev detecta su conexión y crea el nodo de dispositivo en /dev/input/ automáticamente.

Capa 2 — El Kernel Linux
Los 6 subsistemas del kernel y qué hace cada uno

El kernel no es un programa monolítico simple — es una colección de subsistemas especializados que trabajan juntos. Cada subsistema tiene su propio equipo de mantenedores, su propia carpeta en el código fuente y su propia interfaz hacia las capas superiores.

🏥 Analogía — El hospital y sus departamentos

El kernel es como un hospital: tiene un departamento de urgencias (scheduler — asigna atención inmediata), farmacia (gestión de memoria — da recursos y los recupera), quirófanos (sistema de archivos VFS — operaciones de I/O), UCI (subsistema de red — comunicación crítica), mantenimiento (drivers — hablan con el equipamiento) y seguridad (módulos de seguridad — controlan quién entra dónde). Cada uno es esencial y trabaja coordinado con los demás.

SubsistemaCarpeta en fuenteResponsabilidad
Scheduler (CFS)kernel/sched/Decide qué proceso usa la CPU en cada instante. El algoritmo CFS garantiza equidad entre procesos.
Memory Managermm/Gestiona RAM física y virtual. Páginas, swap, malloc, mmap, OOM killer.
VFSfs/Virtual File System — interfaz única para todos los sistemas de archivos: ext4, btrfs, tmpfs, procfs…
Driversdrivers/60%+ del código del kernel. Hablan directamente con el hardware. GPU, red, USB, audio, teclado…
Network Stacknet/TCP/IP, sockets, firewall (netfilter/iptables), routing, interfaces de red.
Securitysecurity/LSM (Linux Security Modules): SELinux, AppArmor, seccomp, capabilities, namespaces.

System Calls — la frontera entre mundos
La única puerta de entrada al kernel desde el espacio de usuario

Las System Calls (syscalls) son la única forma que tiene el código de usuario (apps, shell, bibliotecas) de pedirle al kernel que haga algo privilegiado. Son la interfaz oficial entre User Space y Kernel Space. Linux tiene aproximadamente 350 syscalls definidas.

🏦 Analogía — La ventanilla del banco

Las syscalls son la ventanilla del banco. El banco (kernel) tiene el dinero (recursos: CPU, RAM, disco). Tú (aplicación) no puedes entrar a la cámara acorazada directamente — tienes que ir a la ventanilla, identificarte, pedir lo que necesitas con el formulario correcto, y el cajero (syscall handler) verifica que tienes permiso y hace la operación. Seguro, controlado, auditado.

strace — ver las syscalls que hace un programa en tiempo real
# strace muestra cada syscall que hace un programa — fascinante $ strace ls /tmp 2>&1 | head -20 execve("/usr/bin/ls", ["ls", "/tmp"], ...) = 0 openat(AT_FDCWD, "/tmp", O_RDONLY|O_DIRECTORY) = 3 getdents64(3, 0x5638..., 32768) = 248 write(1, "archivo1.txt archivo2.log\n", 27) = 27 close(3) = 0 # Contar cuántas syscalls hace un comando $ strace -c ls / 2>&1 | tail -15 % time seconds usecs/call calls syscall 45.23 0.000091 9 10 openat 22.11 0.000045 4 10 read 18.04 0.000036 4 9 mmap

💡 Por qué las syscalls son el punto de seguridad crítico

Cada syscall es un punto de control de seguridad. El kernel verifica permisos en cada una: ¿tiene este proceso permiso para leer este archivo? ¿Puede abrir una conexión de red? ¿Puede crear un proceso hijo? Si la respuesta es no, la syscall falla con un error EPERM o EACCES y el proceso nunca llega al hardware. Es por eso que un proceso comprometido no puede hacer daño fuera de sus permisos.

Capas 3-6 — El Userspace
Servicios del sistema, GNU, escritorio y aplicaciones

El userspace (espacio de usuario) es todo lo que corre fuera del kernel. Aquí los procesos tienen privilegios limitados y se comunican con el kernel solo a través de syscalls. Está organizado en sub-capas que dependen unas de otras.

Capa 3 — Servicios del sistema (daemons)

Los daemons son procesos que corren en segundo plano sin interacción del usuario. Arrancan con el sistema (vía systemd) y gestionan recursos compartidos.

systemd
PID 1 — el padre de todos los procesos. Gestiona el arranque y todos los servicios del sistema.
udev
Detecta hardware nuevo (plug & play). Crea nodos en /dev/ cuando conectas un USB o disco.
NetworkManager
Gestiona conexiones WiFi, Ethernet y VPN. Expone una interfaz D-Bus para que otras apps lo controlen.
PulseAudio / Pipewire
Servidor de audio. Mezcla el sonido de múltiples apps (Spotify + Chrome + videollamada) y lo envía al driver.
D-Bus
Sistema de mensajería entre procesos. Las apps se comunican entre sí sin conocerse directamente.
cron / systemd timers
Ejecutan tareas programadas. Backups automáticos, actualizaciones, limpieza de logs.

Capa 4 — GNU y bibliotecas

Las bibliotecas compartidas son código reutilizable que muchas apps usan a la vez. En lugar de que cada app incluya su propia copia de libc, todas usan la misma cargada en memoria.

ver qué bibliotecas usa un programa
# ldd muestra las bibliotecas que carga un ejecutable $ ldd /usr/bin/git linux-vdso.so.1 (0x00007ffeb6bfd000) libpcre2-8.so.0 => /usr/lib/x86_64-linux-gnu/libpcre2-8.so.0 libz.so.1 => /usr/lib/x86_64-linux-gnu/libz.so.1 libc.so.6 => /usr/lib/x86_64-linux-gnu/libc.so.6 # Las bibliotecas compartidas viven en: $ ls /usr/lib/x86_64-linux-gnu/ | head -10 libc.so.6 libm.so.6 libssl.so.3 libpthread.so.0 libcurl.so.4 libgtk-3.so.0 # Ver todas las bibliotecas cargadas en memoria ahora mismo $ cat /proc/$(pidof firefox)/maps | grep "\.so" | awk '{print $6}' | sort -u | head -8 /usr/lib/x86_64-linux-gnu/libdbus-1.so.3 /usr/lib/x86_64-linux-gnu/libgio-2.0.so.0

Capas 5 y 6 — Escritorio y Aplicaciones

El entorno de escritorio (GNOME, KDE) corre en userspace como cualquier otra aplicación — no tiene privilegios especiales salvo los que le otorga el usuario. Las aplicaciones usan las APIs del escritorio (GTK, Qt) que a su vez usan las bibliotecas GNU que a su vez hacen syscalls al kernel.

El sistema de archivos virtual (VFS)
Por qué "todo en Linux es un archivo" — y qué significa realmente

Una de las ideas más poderosas de Unix/Linux es que "todo es un archivo". No solo los documentos — también los dispositivos, los procesos, la configuración del kernel y los sockets de red se representan como archivos. Esto permite usar las mismas herramientas (cat, echo, read, write) para interactuar con todo.

📬 Analogía — El sistema postal universal

Imagina que puedes enviar una carta a cualquier entidad — una persona, una empresa, un cajero automático, una impresora — usando exactamente el mismo formato de sobre y el mismo servicio postal. No necesitas aprender un sistema diferente para cada destinatario. El VFS es ese servicio postal universal — leer un archivo del disco, un dispositivo USB o una conexión de red usa exactamente la misma llamada read().

🟢 /dev/null — el dispositivo más útil

/dev/null es un dispositivo especial que descarta todo lo que se escribe en él y devuelve EOF al leerlo. Es el "agujero negro" de Linux. Extremadamente útil para silenciar la salida de comandos: comando 2>/dev/null descarta los errores. comando &>/dev/null descarta todo. Es un archivo pero no existe físicamente en ningún disco.

Procesos — cómo Linux gestiona la ejecución
PID, fork/exec, señales y el árbol de procesos

Cada programa en ejecución es un proceso. Linux identifica cada proceso con un número único llamado PID (Process ID). El sistema arranca con systemd como PID 1 y todos los demás procesos son hijos o descendientes de él.

# El árbol de procesos de Linux PID 1 systemd ← el primer proceso, padre de todos ├── PID 2 kthreadd ← hilos del kernel ├── PID 847 NetworkManager ← servicio de red ├── PID 901 gnome-shell ← escritorio GNOME │ ├── PID 1203 firefox ← navegador │ │ └── PID 1890 firefox ← proceso de pestaña │ └── PID 1250 code ← VS Code └── PID 950 bash ← tu terminal └── PID 2847 python3 ← script que lanzaste

fork() y exec() — cómo nacen los procesos

En Linux todos los procesos nacen de la misma forma. No se "crean desde cero" — se clonan y luego se transforman:

# bash lanza un nuevo programa (ej: git clone) bash (PID 950) │ ├─ fork() → crea una copia exacta de bash (PID 1100) │ mismo código, misma memoria, mismo estado │ └─ PID 1100 llama exec("git", ["git","clone","..."]) → reemplaza su propio código por el de git → ahora PID 1100 ES git corriendo # bash espera (wait()) a que PID 1100 termine # cuando git termina, bash recupera el control

Flujo completo — de un clic a los transistores
Trazando exactamente qué ocurre cuando abres un archivo en Firefox

Juntemos todo lo que hemos visto siguiendo el camino completo de una acción concreta: haces clic en "Guardar archivo" en Firefox. ¿Qué ocurre en cada capa?

# Tú haces clic en "Guardar" en Firefox Capa 6 — App Firefox detecta el clic → llama a sus APIs internas → decide escribir el archivo Capa 5 — Escritorio GTK (biblioteca gráfica) procesa el evento del ratón → notifica a Firefox Capa 4 — GNU/glibc Firefox llama a fopen() de glibc → glibc convierte esto a syscalls ══════ FRONTERA KERNEL/USER — System Call ══════ Capa 2 — Kernel syscall open() → VFS verifica permisos → crea file descriptor syscall write() → VFS selecciona el sistema de archivos (ext4) → ext4 calcula dónde escribir en el disco → I/O scheduler optimiza el orden de escrituras → driver NVMe envía el comando al controlador Capa 1 — Hardware SSD NVMe recibe el comando → escribe los datos en sus celdas flash → envía confirmación al kernel → kernel notifica a Firefox → Firefox muestra "archivo guardado" Tiempo total: ~1-5 milisegundos

📌 Por qué importa entender este flujo

Cuando algo falla — un archivo no se guarda, una conexión no funciona, una app crashea — este mapa te dice dónde buscar. ¿Falla en la capa de app? ¿Es un problema de permisos en el kernel? ¿El driver del disco tiene un bug? ¿El sistema de archivos está lleno? Sin este modelo mental, los problemas de Linux parecen magia negra. Con él, son diagnósticos sistemáticos.

✏️ Ejercicio del Nivel 9 Exploración

Explora las capas de Linux desde tu terminal (Ubuntu, Fedora, o cualquier distro):

  1. Hardware: ejecuta lspci, lsusb y lsblk. Identifica tu GPU, tu NIC y tus discos. ¿Coinciden con las especificaciones de tu equipo?
  2. Kernel: ejecuta cat /proc/cpuinfo | grep "model name" | head -1 y cat /proc/meminfo | head -3. ¿Qué ves?
  3. Módulos: ejecuta lsmod. ¿Ves el driver de tu WiFi o GPU? Búscalo: lsmod | grep -i nvidia o lsmod | grep -i wifi.
  4. Syscalls: instala strace (sudo apt install strace) y ejecuta strace ls /tmp 2>&1 | head -15. ¿Puedes identificar las syscalls open, read y write?
  5. Procesos: ejecuta pstree -p | head -20. ¿Ves a systemd como PID 1? ¿Puedes trazar el árbol hasta tu terminal?
  6. VFS: ejecuta cat /proc/version y cat /sys/class/net/lo/address. ¿Ves cómo el kernel expone información como archivos de texto?
  7. Bibliotecas: ejecuta ldd $(which ls). ¿Cuántas bibliotecas usa el comando ls?

Reflexión: Ahora que conoces las capas, cuando algo falla en tu sistema Linux, ¿en qué capa buscarías primero el problema? ¿Por qué?

🟥 Resumen del Nivel 9

  • Linux tiene 6 capas: Hardware → Kernel → Servicios → GNU/libs → Escritorio → Apps.
  • Cada capa solo se comunica con sus vecinas — nadie salta pisos. Esto garantiza seguridad y estabilidad.
  • El Kernel tiene 6 subsistemas: scheduler, memory manager, VFS, drivers, network stack y security.
  • Las System Calls son la única puerta entre User Space y Kernel Space. Linux tiene ~350 syscalls.
  • strace permite ver en tiempo real qué syscalls hace cualquier programa.
  • "Todo es un archivo" — dispositivos (/dev/), procesos (/proc/), configuración del kernel (/sys/) son archivos.
  • Todos los procesos nacen de fork() (clonar) + exec() (transformar). PID 1 es systemd.
  • Entender el flujo completo (clic → transistor) permite diagnosticar cualquier problema de forma sistemática.
